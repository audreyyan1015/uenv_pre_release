## 3. SWE 在线训练数据与策略

本周将后训练目标聚焦到 SWE 任务，并明确第一阶段采用在线 RL/RLVR，而不是先做 SFT。

已形成文档：

```text
docs/SWE任务UEnv训练数据准备与训练策略.md
```

当前训练策略如下：

| 阶段 | 数据规模 | 训练步数 | 目标 | 通过标准 |
|---|---:|---:|---|---|
| 环境 smoke | 5 到 20 条 | 0 | 验证 Worker/OpenHands 可执行，排除坏样本 | 每条样本能返回 completed/failed/resolved |
| 1-step RL smoke | 2 到 4 条 | 1 | 验证 VeRL 能消费 SWE result 并完成一次 update | VeRL step 完成，reward 有效，request/result 数量对齐 |
| 10-step 小跑 | 20 到 100 条 | 10 | 观察耗时、显存、reward 分布和失败类型 | 无 OOM，失败主要来自模型未解决 |
| 子集训练 | 100 到 500 条 | 50 到 200 | 观察 reward/resolved 是否有趋势 | 固定验证子集有可解释变化 |
| 训练外评测 | SWE-bench-Pro 731 条 | 0 | 回归 public test | 与当前基线 `106/731=14.50%` 对比 |

数据边界已经明确：`SWE-bench-Pro public test` 继续作为训练外评测集，不进入训练数据。训练侧优先使用可执行任务池、SWE-Gym、SWE-smith 或自建 issue-fix 任务。

结论：SWE 训练的第一目标不是直接追求分数提升，而是先证明 UEnv 在线环境、OpenHands agent、Worker reward 和 VeRL GRPO batch 能形成可信训练闭环。

## 5. SWE GRPO Rollout Trace 诊断

本周最关键的问题是：SWE/OpenHands 是多轮 agentic 任务，VeRL GRPO 不能只用最终文本或 pad token 训练，必须拿到 episode 内多次 LLM action 的 token trace。

已整理跨层说明：

```text
Docs/adapter/20260802-SWE-GRPO训练缺少rollout-trace诊断说明.md
```

当前要求 Worker/OpenHands 在 `AgentJobCompleteRequest` 中返回：

| 字段 | 要求 |
|---|---|
| `rollout_trace.response_ids` | 所有需要参与训练的 assistant token id，按 OpenHands 多轮 LLM 调用顺序拼接 |
| `rollout_trace.response_mask` | 与 `response_ids` 等长，当前建议全为 1 |
| `rollout_log_probs` | 与 `response_ids` 严格等长，逐 token 对齐的 old policy logprob |

定位到的历史问题是：8 条 SWE episode 可以完成，gateway 也能返回 HTTP 200，VeRL 能继续执行 `old_log_prob/ref/update_actor/update_weights`，但 Adapter 侧实际看到的是：

```text
response_source=empty
used_pad_fallback=true
rollout_log_probs_len=0
response_ids=[]
verl_response_ids=[248044]
```

这只能说明链路能跑，不能说明 SWE GRPO 训练有效。

本周合并 Worker/OpenHands 侧修复后，已执行：

```text
python3 -m pytest integrations/openhands/tests -q
```

结果为：

```text
12 passed, 1 skipped
```

并对 OpenHands/runner 相关 Python 文件完成 `py_compile` 检查。

结论：SWE GRPO 所需字段的工程入口已经补齐，Adapter 也保留 `UENV_REQUIRE_SWE_RESPONSE_TRACE=1` 的 fail-fast 保护。下一步需要以真实 SWE-smith LLM episode 复测，确认 `agent-loop-results.jsonl` 中出现 `response_source=rollout_trace`、`used_pad_fallback=false`、`rollout_log_probs_len == len(response_ids)`。

本周继续补充 NexRL 调研，重点从“整体架构对比”扩展到“环境接入与 UEnv 对齐”。


当前结论：

| 方向 | 结论 |
|---|---|
| RolloutWorker | NexRL 的 `BaseRolloutWorker` 只定义通用框架，环境交互由派生类或 Agent 实现 |
| AgentRolloutWorker | 简单任务等价于 prompt + LLM generate + rule reward |
| BaseNexAURolloutWorker | 复杂 agentic 任务通常通过 NexAU agent 和工具调用过程隐藏环境交互 |
| TrajectoryPool | 对 UEnv 未来 fully async result/trajectory pool 有参考价值 |
| WeightSyncController | 对模型版本、推理服务更新和多副本同步有参考价值，但多副本推理同步仍需额外设计 |

结论：NexRL 更适合作为 UEnv 长期服务化架构参考。短期主线仍应继续把 VeRL + UEnv 的 SWE 在线训练跑通，再决定是否投入 NexRL 原生 smoke 或 UEnv RolloutWorker 接入。
