## 2. SWE-smith GRPO 训练入口与配置

本周继续将 SWE-smith 作为第一阶段 SWE 在线训练数据，训练入口集中在：

```text
uenv-bridge/scripts/train/launchers/swe/swe_smith_grpo_train.sh
uenv-bridge/scripts/train/launchers/common/run_verl_uenv_grpo.sh
```

当前训练脚本的主要职责是准备 SWE-smith VeRL parquet、配置 UEnv AgentLoop、启动 adapter-side model gateway，并把请求送到 Server 侧 Rust AdapterCore。训练侧仍采用全参数 GRPO，当前阶段先不做 SFT，也不启用 LoRA。

代表性配置如下：

| 配置项 | 当前口径 |
|---|---|
| 基座模型 | `Qwen/Qwen3.6-35B-A3B` |
| 训练框架 | VeRL GRPO + UEnv AgentLoop |
| 环境执行 | UEnv Worker + OpenHands + SWE-smith |
| GPU 资源 | 8 卡，`ROLLOUT_TP=8` |
| `TRAIN_BATCH_SIZE` | `2` |
| `ROLLOUT_N` | `4` |
| 每个 rollout batch episode 数 | `8` |
| `DATA_MAX_RESPONSE_LENGTH` | `8192` |
| gateway `max_tokens` | `4096` |
| SWE agent 最大步数 | `SWE_TRAJECTORY_MAX_STEPS=50` |
| trace 要求 | `UENV_REQUIRE_SWE_RESPONSE_TRACE=1` |
| failed episode 策略 | `UENV_AGENT_LOOP_FAILED_EPISODE_POLICY=zero_reward` |
| wandb | 支持 `TRAINER_LOGGER=['console','wandb']` 和 `WANDB_ENV_FILE` |

结论：脚本已经具备正式训练入口形态，并能通过 `--limit`、`--offset` 控制训练数据切片。后续需要继续观察 8GPU 长时间训练下的 step 耗时、显存峰值、response 截断比例和 reward 稳定性。

## 3. Worker 并行与调度口径

本周围绕 SWE-smith rollout 慢的问题梳理了 Worker 侧并行能力。当前结论是：Adapter 训练入口负责按 VeRL batch 生成 episode 请求；实际 Worker 并行度由 Server/Worker 根据资源、Worker pool、OpenHands agent 池和 Runtime Gateway session 统一调度。

Adapter 侧不再向请求协议中写入期望 Worker 并行数或调度提示字段，避免训练侧参数与 Worker 真实资源状态不一致。当前阶段采用 Worker 侧固定并行数 4 的方案，后续继续通过训练日志和前端观测确认实际并行是否生效。

## 4. 长轨迹 gRPC 传输修复

SWE/OpenHands episode 会返回多轮工具轨迹、`response_ids`、`response_mask`、`rollout_log_probs` 等字段，单个 batch 的 `EpisodeResult` 容易超过 gRPC 默认 4 MiB。

已记录文档：

```text
Docs/adapter/20260808-gRPC消息上限链路核验与Server补齐说明.md
uenv-bridge/docs/任务训练/SWE-smith GRPO 训练问题记录.md
```

代表性错误：

| run | 错误 |
|---|---|
| `verl_swesmith_grpo_train_20260808_080059` | `4646840 vs. 4194304` |
| `verl_swesmith_grpo_train_20260808_152436` | `4594969 vs. 4194304` |

已补齐的链路：

| 链路 | 当前上限 |
|---|---:|
| Python Adapter -> Rust AdapterCore client | 16 MiB |
| Rust AdapterCore service | 16 MiB |
| Rust Server -> Worker client | 16 MiB |
| Worker runtime gRPC service | 16 MiB |

结论：4 MiB 超限问题已经从 Adapter/Server/Worker 链路上完成工程补齐。若后续单条 SWE/OpenHands trajectory 继续膨胀，仍需要继续评估 32 MiB 上限或 result 体积裁剪。

## 5. SWE-smith Reward 与 Runtime Contract

本周重点定位了此前 SWE-smith GRPO 训练中 `reward=0`、`resolved=false` 的根因范围。相关文档：

```text
uenv-bridge/docs/任务训练/SWE-smith GRPO 训练问题记录.md
Docs/adapter/20260809-SWE-smith-GRPO初始环境与Reward核验说明.md
Docs/worker/260809/SWE运行时语义Contract与Smith-Pro兼容修复报告.md
```

已定位问题包括：

| 问题 | 现象 | 结论 |
|---|---|---|
| 官方 harness 与内部 grader 不一致 | gold patch 在官方 harness 下 resolved true，但旧 UEnv gateway/internal grader 下 resolved false | SWE-smith reward 需要以官方 harness 口径为准 |
| 镜像命名空间不一致 | 官方使用 `swebench/swesmith...`，旧 catalog 存在 `jyangballin/swesmith...` | 需要对齐官方镜像和 catalog |
| 初始环境没有注入 bug baseline | agent 进入 `/testbed` 后已经看到 clean/fixed 状态，无法复现 prompt 中的 bug | Worker provision 需要先注入 SWE-smith bug-inducing patch |
| Smith 与 Pro patch 方向不同 | Smith 数据集 patch 是 clean -> buggy，Pro 通常是 bug -> fix | 需要用 runtime contract 显式表达任务语义 |

Worker 侧最新改动将环境语义从代码分支逻辑推进到可扩展 contract。当前约定大致为：

| Benchmark | workspace | patch 语义 | provision | gold |
|---|---|---|---|---|
| SWE-smith | `/testbed` | clean -> buggy | 应用数据集 patch 后提交 bug baseline | 反向应用数据集 patch |
| SWE-bench-Pro | `/app` | bug -> fix | 使用已准备好的 buggy repo | 正向应用数据集 patch |

结论：此前全 0 reward 不能只归因于模型能力。Worker 侧修复后，Adapter 最新训练结果已经出现非零 reward，说明 reward 和初始环境语义正在恢复到可训练状态。

## 7. 可观测性与前端联调

本周继续配合前端和 Server Obs 联调，重点集中在训练/评测 run 的展示入口、Worker fleet 状态和 episode 事件聚合口径。

相关变化：

| 项 | 进展 |
|---|---|
| 训练脚本 | 补充 `UENV_OBS_URL`、`UENV_OBS_TOKEN`、`UENV_TRAINING_RUN_ID` |
| 前端 demo | 将用户侧训练/评测页面收敛为“训练任务、Benchmark 测评、脚本模板”三个入口 |
| Server 页面 | 合并 Server 侧 Worker 详情和 fleet 状态页面，用于查看 Worker 是否在线、是否注册、容量是否为 0 |
| 事件口径 | 确认前端统计依赖 Server/Worker 投递的 episode 事件，Adapter 仅上报 run 边界无法让 workflow 各阶段计数完整 |

当前仍需对齐的问题：

| 问题 | 当前判断 |
|---|---|
| `DISPATCH/EXECUTE` 关联实体为 0 | Server/Worker 需要把对应 episode 状态事件投递到同一个 Obs run |
| failed episode 没有显示为失败终态 | 需要 Server/Worker 或 Adapter fallback 补发 `EPISODE_FAILED/EPISODE_CLOSED` |
| 页面提示未配置 server 地址 | 前端部署需要配置 `VITE_AGGREGATION_BASE_URL` 等环境变量 |

结论：可视化入口已经能承接训练 run，但训练态细节展示是否准确取决于 Server/Worker 的 episode 事件上报完整性。
