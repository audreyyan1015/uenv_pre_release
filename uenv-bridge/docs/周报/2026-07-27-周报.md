## 2. 五类 Benchmark 基准模型评测

本周完成了 `Qwen/Qwen3.6-35B-A3B` 在五类 benchmark 上的 Eval-first 基线评测。本阶段不进行 SFT/RL 后训练，目标是先验证 UEnv 全链路在不同任务形态下能否稳定完成请求、推理、环境执行、判分和结果聚合。

统一链路如下：

```text
Benchmark 数据集
  -> Adapter driver 构造 EpisodeRequest
  -> Adapter Core / Server
  -> Worker 按 env_type 和 dataset 路由
  -> Worker 访问 Adapter Model Gateway
  -> Gateway 转发到本机 vLLM
  -> Worker 执行解析、判分、代码运行或 agent 任务
  -> EpisodeResult 返回 Adapter
  -> Adapter driver 汇总指标
```

最终结果汇总如下：

| 任务书条目 | Benchmark | 数据规模 | 当前状态 | 主指标 | 当前结果 |
|---|---|---:|---|---|---:|
| 1. 文本阅读理解 | PubMedQA | 1000 | UEnv 全量完成 | Accuracy / Macro-F1 | 0.8000 / 0.5912 |
| 2. 表格理解 | SciTab | 1224 | UEnv 全量完成 | Accuracy / Macro-F1 | 0.7451 / 0.7340 |
| 3. 代码生成 | DSCodeBench | 1000 | UEnv 全量完成 | pass@1 | 0.2810 |
| 4. 测试生成/程序修复 | SWE-bench-Pro | 731 | UEnv 全量完成 | resolved / resolve rate | 106 / 14.50% |
| 5. 数学题求解 | OlymMATH | 400 | UEnv 全量完成 | UEnv reward accuracy | 0.6575 |

五类任务已经统一记录到 `docs/任务测评/五类Benchmark基准模型基准测试.md`，各任务也分别形成了独立测评文档。PubMedQA、SciTab、OlymMATH 和 DSCodeBench 均完成全量请求与结果回收；SWE-bench-Pro 也完成 731 条全量运行，并从早期 `resolved=0` 的状态推进到有效基线 `106/731=14.50%`。

结论：UEnv 在文本分类、表格理解、数学求解、代码生成和 agentic 程序修复五类任务上的评测链路已经闭合。后续可以基于这组基准结果选择更适合 RL/RLVR 的任务，并进一步分析代码类与 SWE 类任务中的失败来源。

## 3. NexRL 架构调研

本周调研了 NexRL 的系统结构，并整理了两份文档：

```text
docs/NexRL架构与VeRL-ROLL对比调研.md
docs/NexRL调研与最小样例规划.md
```

NexRL 与 VeRL / ROLL 的主要差异在于它把后训练流程拆成多个服务化组件，而不是主要依赖单个 trainer 入口组织完整训练流程。

| 组件 | 职责 | 对 UEnv 的参考价值 |
|---|---|---|
| `RolloutWorker` | 负责采样、环境交互、reward 计算和 trajectory 生成 | 可作为未来 UEnv rollout 接入点参考 |
| `TrajectoryPool` | 缓存并聚合 rollout 结果，供 Trainer 消费 | 对 UEnv 后续 async result pool / trajectory pool 设计有借鉴意义 |
| `Trainer` / `Train Service` | 执行算法逻辑，并通过服务化接口适配训练后端 | 有利于理解训练后端解耦方式 |
| `Inference Service` | 通过 OpenAI-compatible API 对接 vLLM、SGLang、TGI 等推理后端 | 与当前 Adapter Model Gateway 设计方向接近 |
| `WeightSyncController` | 协调训练后权重同步到推理服务 | 对多副本推理和模型版本一致性问题有参考意义 |

调研结论是：NexRL 更适合作为 UEnv 长期服务化架构参考，尤其适合研究 rollout、training、trajectory pool 和 weight sync 解耦后的系统形态。但它的启动和调试复杂度高于 VeRL / ROLL，因此短期不建议立即接入 UEnv，而是先跑通 NexRL 原生 GSM8K 1step / 10step 最小样例，再判断是否进入实际集成。

## 4. 可视化联调与 Debug

本周协助推进了 UEnv 可视化观测链路的真实联调和前端交互修复。当前可视化数据流是 Server 侧聚合：Adapter / Server / Worker 等模块产生事件后进入 `uenv-server` 内嵌 Obs，前端通过 REST / SSE 订阅 `ChainState` 并展示训练运行状态。

真实 Obs smoke 已经验证了 `qa` 四类样例可以完成端到端观测：

| 检查项 | 结果 |
|---|---|
| `gsm8k`、`pubmedqa`、`scitab`、`olymmath-easy` | 全部 `completed/reward=1` |
| `run_state` | `CLOSED` |
| workflow | `SUBMIT/DISPATCH/EXECUTE/REPORT/DONE` 全部完成 |
| tree root / step 状态 | 经 Server Obs 状态收口后可正确关闭 |

前端侧主要完成了三类交互修复：

| 功能 | 本周处理 |
|---|---|
| 页面布局 | 将页面调整为一屏内控制台布局，避免整体页面大范围横向或纵向滚动 |
| 面板拖拽 | 引入可拖拽分隔面板，支持调整工作流、对象树、详情和事件流区域大小 |
| workflow 交互 | 修复工作流视图中的定位、居中、全屏、缩小、放大按钮，使其具备真实交互能力 |

同时定位了 workflow 卡片中“关联实体=0”的原因：前端读取的是 `workflow.nodes[].payload_summary.count`，如果 Server Obs 未填充该字段，页面会显示为 0。这一问题不应只由前端推断修复，后续建议由 Server Obs projection / merge 层维护权威计数。

结论：可视化主链路已经具备真实 run 展示能力，前端布局和交互可用性明显改善；剩余工作主要是补齐 Server Obs 的统计摘要字段和更细粒度的运行指标。
