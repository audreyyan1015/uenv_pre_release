# UEnv+VeRL 与原生 VeRL 方案 D1：固定墙钟的有效训练量对比

## 1. 方案目标

这套方案不再只看固定 step 数下谁更快，而是看在相同墙钟时间 `T` 内，谁真正产出了更多“可用训练量”。

最终对外主指标建议看这三项：

| 主指标 | 含义 |
| --- | --- |
| 有效 episode 数 / 非零 reward episode 数 | 在相同时间内，真正进入训练闭环并产生有效信号的样本数 |
| holdout resolve rate | 训练前后，在同一组 100 条 holdout 上的 resolved 比例 |
| 有效 GRPO step 数 | 过滤掉失败重试、未进入 update 的 step 之后，真正完成参数更新的 step 数 |

这套方案的核心不是证明 UEnv 单条 episode 的绝对最短延迟，而是证明它在故障、并发和多 worker 场景下，能不能在同样时间里保住更多有效训练产出。

## 2. 为什么改成 D1

前一版按固定 step 对齐的测试，已经能看出 UEnv+VeRL 在当前链路里有额外调度开销。但这种对比只回答“谁单步更快”，回答不了下面这些更重要的问题：

- 故障出现后，谁丢掉的 episode 更少
- worker 槽位被长尾任务占住时，谁能更快补上新任务
- 同样 6 到 12 小时里，谁真正更新了更多有效 step
- 最终同一 holdout 上，谁更稳地把结果做出来

所以 D1 的目标是把“速度”改成“有效训练量 + 故障恢复能力”。

## 3. 任务范围建议

为了避免完整 SWE-smith 全量部署，建议只裁剪出本轮训练需要的固定子集，并把对应镜像同步到参与实验的 worker 机器上。

建议分两层：

| 层级 | 任务范围 | 用途 |
| --- | --- | --- |
| Smoke | 20 条训练样本 + 20 条 holdout | 先验证链路和 catalog 裁剪是否正确 |
| D1 主实验 | 100 条训练样本 + 100 条 holdout | 作为正式对比范围，足以支撑墙钟窗口内的统计 |

这 200 条样本要在实验开始前冻结成固定列表，后续所有对比都复用同一份顺序、同一份 catalog 和同一份 holdout。

catalog 只保留本轮要跑的镜像集合，不需要完整 SWE-smith 全量包。对 UEnv 来说，推荐把这些镜像分发到至少两台 worker 服务器上，形成真实的多 worker 协作。

## 4. 工况设置

### 4.1 训练与资源

| 项目 | 设置 |
| --- | --- |
| 训练 GPU | 两侧都用 8 卡 |
| 模型 | 同一 checkpoint |
| 算法 | 同一 GRPO 配置 |
| 数据 | 同一训练子集、同一 holdout 子集、同一顺序 |
| batch | 每 step 16 到 32 个 episode |
| 时间窗口 | 固定 `T=6~12h` |

### 4.2 UEnv 侧

| 项目 | 设置 |
| --- | --- |
| Worker 服务器 | 至少 2 台，例如 7143 + 另一台 CPU 机 |
| 并发策略 | Agent 并发从 4 -> 8 -> 16 阶梯测试 |
| catalog | 只部署本轮实验需要的镜像 |
| 调度目标 | 尽量吃满 worker 槽位，观察 slot refill 和 reclaim 效果 |

### 4.3 native VeRL 侧

| 项目 | 设置 |
| --- | --- |
| 环境接入 | 原生 VeRL + 自定义 AgentLoop |
| worker 侧形态 | 默认保持单路径或更简陋的执行面 |
| 故障恢复 | 以全量重启、重新拉起或人工重试为主 |

这里故意保留一个差异：native 侧的恢复方式可以更简单，UEnv 侧则强调多 worker 注册、任务回收和继续调度。这样更容易看出系统调度能力的差距。

## 5. 故障注入

这是 D1 的关键。

| 注入项 | 频率 | 目的 |
| --- | --- | --- |
| kill 1 个 agent slot | 每小时 1 次 | 看单槽损坏后能否继续推进 |
| 断 Gateway 60 秒 | 每小时 1 次 | 看请求入口恢复后是否能接着跑 |
| 可选：重启 Server / AgentControl | 按需 | 看调度层是否能快速恢复 |

native 侧故障处理建议保持粗粒度，比如直接重启、重新拉起、或者简单重试。不要在 native 侧额外补太多恢复逻辑，否则就失去这次对比的系统意味了。

## 6. 主要对比指标

### 6.1 最终主指标

| 指标 | 说明 |
| --- | --- |
| 有效 episode 数 | 成功进入执行并返回有效结果的 episode 数 |
| 非零 reward episode 数 | 真正产生训练信号的 episode 数 |
| holdout resolve rate | 同一 holdout 集上的训练前后结果 |
| 有效 GRPO step 数 | 真正进入 update 的 step 数 |

### 6.2 辅助指标

| 指标 | 说明 |
| --- | --- |
| step time | 单 step 耗时 |
| rollout time | 采样和环境交互耗时 |
| 故障恢复时间 | 从故障注入到恢复稳定推进的时间 |
| episode 丢失率 | 故障后没能进入训练闭环的 episode 占比 |
| worker 利用率 | 槽位是否被吃满 |
| 吞吐 | episodes/hour |

## 7. 为什么这套方案更适合拉开差距

UEnv 的优势不应只看单条 episode 的局部性能，而应看下面这些系统能力：

- 多 worker 注册后，谁能更快把空槽重新填满
- 某个 worker 慢了以后，谁更容易继续推进其他 episode
- 故障发生后，谁丢掉的训练量更少
- 墙钟时间固定时，谁能把更多 episode 变成真正的有效训练步

如果只跑固定 step 数，差距很容易被平均掉；如果引入墙钟窗口和故障注入，调度算法、worker 扩展和恢复能力就更容易显出来。

## 8. 结论口径

建议 D1 对外这样表述：

1. 我们在相同墙钟时间内对比原生 VeRL 和 UEnv+VeRL。
2. 主指标不是单步速度，而是有效 episode、有效 step 和 holdout resolve rate。
3. 通过故障注入和多 worker 协作，UEnv 的系统价值会更容易被看见。
4. catalog 不用做全量部署，只保留本轮实验实际需要的镜像集合即可。
