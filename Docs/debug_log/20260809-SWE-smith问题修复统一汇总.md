## 问题与修复

### 1. Worker 最初只加载 SWE-smith smoke catalog

现象：

```text
swe instance_id ... not in catalog (size=736)
```

核验发现 `736 = SWE-bench-Pro 731 + SWE-smith smoke 5`。Worker 的 Smith catalog 实际只有 5 条 oauthlib smoke instance，而不是全量 SWE-smith。

修复：

- 在 7143 导出并挂载全量 SWE-smith EnvPackage。
- catalog 从 5 条扩展到 59136 条。
- Gateway 合并 catalog 从 736 扩展到 59867 条。
- EnvPackage 路径：

```text
/var/lib/uenv/envs/swe-bench-smith/0.1.0-local
  -> /data/uenv/envs/swe-bench-smith/0.1.0-local
```

关联记录：

- `Docs/adapter/20260804-SWE-smith-Worker数据集覆盖核验说明.md`
- `Docs/worker/260802/SWE-smith全量catalog补齐与Worker重启报告.md`

### 2. 全量 catalog 后 OpenHands 仍命中旧 smoke fixture

现象：

Worker 侧已加载全量 catalog，但 OpenHands driver 仍报：

```text
instance ... not in /root/UEnv/fixtures/swe/smith_catalog.json
```

根因：

Agent 侧没有全量 EnvPackage 文件，driver 的 catalog fallback 顺序仍优先命中本地 5 条 smoke fixture。Worker 内存 catalog 只服务 Gateway 查表/provision，不能自动让 208.77 driver 拿到全量 instance。

修复：

- 7143 Runtime Gateway 新增单样本查询：

```text
GET /runtime/v1/instances/{instance_id}
```

- 208.77 OpenHands driver 本地 miss 时通过 Gateway 拉取单条 instance，并写入本次 run 的 `instance_catalog.json`。
- driver 避免整文件读取 4.9 GiB 全量 catalog。
- `scripts/run-openhands-pro-20877.sh` 和 `openhands_runner.py` 对 smith 任务清除 Pro catalog 环境变量，避免串到 SWE-bench-Pro。

关联记录：

- `Docs/adapter/20260804-SWE-smith全量catalog修复后仍命中旧fixture诊断说明.md`
- `Docs/worker/260802/SWE-smith全量catalog后OpenHands仍命中旧fixture-诊断与修复.md`

### 3. Workspace 语义曾串到 SWE-bench-Pro 的 `/app`

现象：

Smith 任务 workspace 应为 `/testbed`，但早期 OpenHands pre-submit 曾写死 `git -C /app`，导致真实 LLM rollout 在提交前失败。

修复：

- `run_swebenchpro_official.py` / `run_swesmith_official.py` 改为使用任务 payload 中的 `workspace_dir`。
- Smith 默认 workspace 固定为 `/testbed`。

关联记录：

- `Docs/worker/260801/SWE-smith变更与联调报告.md`

### 4. 镜像命名空间与官方 SWE-smith harness 不一致

现象：

同一 instance 的官方 harness gold 能 resolved，但 UEnv 内部路径 gold 仍 reward 0。

对照结果：

```text
official image: swebench/swesmith.x86_64.oauthlib_1776_oauthlib.1fd52536
old UEnv image: jyangballin/swesmith.x86_64.oauthlib_1776_oauthlib.1fd52536:latest

official gold: resolved=true, FAIL_TO_PASS 13/13, PASS_TO_PASS 660/660
old UEnv gold: resolved=false, tests=531/673
```

根因：

UEnv catalog / fixture / training parquet 中仍有旧 `jyangballin/swesmith...` 镜像命名空间，而官方 SWE-smith harness 使用 `swebench/swesmith...`。

修复：

- `uenv-worker/src/swe/dataset.rs` 对 Smith image 归一化到 `swebench/swesmith...`。
- `scripts/export_swe_smith_instances.py` 导出 catalog 时使用官方镜像。
- `uenv-bridge/scripts/utils/prepare_verl_swesmith_train.py` 生成 VeRL parquet 时使用官方镜像。
- smoke fixture / config 同步改到官方镜像。

关联记录：

- `Docs/worker/260807/SWE-smith官方Harness判分对照校验.md`
- `Docs/worker/260807/SWE-smith官方镜像与Reward对齐修复记录.md`

### 5. Worker 内部 pytest parser 不能作为最终 SWE-smith reward 权威来源

现象：

内部 `SwesmithGrader` 的 FAIL_TO_PASS / PASS_TO_PASS parser 与官方 `swesmith.harness.eval` 并非完全等价。镜像未对齐时，内部 parser 会把 gold 判成 0。

修复：

- 7143 Worker 配置 `UENV_SWE_SMITH_EVAL_CMD`。
- Worker submit 时先捕获 agent/model 产生的 `/testbed` `git diff`。
- 将捕获到的 model patch 交给官方 SWE-smith harness 单实例评测。
- 最终 `resolved/reward` 以官方 report 为准，内部 pytest 结果只保留为诊断字段。

关键环境变量：

```text
UENV_SWESMITH_REPO=/tmp/uenv-swesmith-official-check/SWE-smith
UENV_SWE_SMITH_EVAL_CMD="/tmp/uenv-swesmith-official-check/venv/bin/python /root/UEnv/scripts/eval_swesmith_official_reward.py"
```

关联记录：

### 6. Smith `patch` 语义在 8/7 与 8/9 之间被重新确认

历史结论：

早期 8/1 文档认为 SWE-smith `patch` 是造 bug 补丁：

```text
provision: git apply patch
gold: git apply -R patch
```

8/7 官方 harness 对照后，文档中曾记录“移除 Worker provision 阶段的 bug patch 预注入”，理由是希望保持 clean base + model_patch 评测语义。

8/9 重新联调结论：

在 UEnv + OpenHands 训练链路中，Worker 创建 Smith session 后如果不把数据集 `patch` 注入为 bug baseline，Agent 看到的是 clean/fixed base，实际 bug 不存在。模型即使提交也难以形成有效的“从 bug 到 fix”的 diff，GRPO rollout 不能反映真实修复任务。

`Docs/adapter/20260809-SWE-smith-GRPO初始环境与Reward核验说明.md` 中记录了具体证据：

```text
run: verl_swesmith_grpo_train_20260808_185234
instance_id: oauthlib__oauthlib.1fd52536.combine_file__oni9ccvi
trajectory_id: trj-worker-7143-pro-1786188520094-00031
prompt expected bug: Content-Type application/xml / Status 500
agent reproduction observed: Content-Type application/json / Status 200
local test: tests/oauth2/rfc6749/endpoints/test_metadata.py 7 passed
git_diff_bytes: 0
resolved: false
tests: 531/673
```

该样本原始 parquet 中的 `patch` 方向为 clean -> buggy：

```diff
- 'Content-Type': 'application/json'
+ 'Content-Type': 'application/xml'
- return headers, json.dumps(self.claims), 200
+ return headers, json.dumps(self.claims), 500
```

因此 agent 交互式训练必须先把 workspace 准备成 buggy 状态，再让 agent 生成 buggy -> fixed 的修复 diff。

最终修复：

- `uenv-worker/src/swe/session.rs`
  - `SweSession::provision()` 后执行 `run_smith_bug_setup_at_provision()`。
  - Smith 专用逻辑：正向应用数据集 `patch`，然后 `git add -A && git commit -m 'uenv smith bug baseline'`。
  - 后续 Agent 修改产生的 `git diff` 表示“从 bug baseline 到 fix”的 model patch。
- `uenv-worker/src/swe/harness.rs`
  - native harness 的 Smith gold patch 改为 `apply_patch_reverse()`。

注意：

8/7 文档中“移除 provision 阶段 bug patch 预注入”的结论已被 8/9 真实训练联调修正。后续以本节为准。

验证：

```text
gold smoke:
run_id: codex-smith-gold-20260809-134632
instance: oauthlib__oauthlib.1fd52536.combine_file__0fceycuu
resolved=true
reward=1.0
```

### 8. 上下文预算边界超限

现象：

训练日志中出现：

```text
This model's maximum context length is 131072 tokens.
However, you requested 4096 output tokens and your prompt contains at least 126977 input tokens,
for a total of at least 131073 tokens.
```

根因：

模型请求使用固定 `max_tokens=4096`，没有根据 prompt tokens 动态收缩输出预算。部分样本只比上限多 1 token，也会被 vLLM 拒绝。

处理状态：

本次 8/9 验证通过选小样本、限制 response length 与可运行 oauthlib 子集避开该问题。长期仍建议在 model gateway 或 OpenHands LLM adapter 中按：

```text
max_tokens = max_model_len - prompt_tokens - margin
```

动态 clamp，margin 建议 64 或 128。

关联记录：

- `Docs/worker/260807/SWE-smith_GRPO训练reward全0与上下文超限瓶颈分析.md`

### 9. 训练预处理依赖在宿主机缺失

现象：

在 7142 以 `ronghao` 用户直接运行：

```bash
scripts/train/launchers/swe/swe_smith_grpo_train.sh
```

预处理阶段报错：

```text
ModuleNotFoundError: No module named 'pandas'
```

根因：

`prepare_verl_swesmith_train.py` 在宿主机 Python 中执行，但 7142 宿主机 root/ronghao Python 均未安装 pandas。VeRL 容器内有 pandas 2.3.3。

本次处理：

- 使用 VeRL 镜像内 Python 生成训练 parquet：

```text
data/benchmarks/swesmith_train_limit8_offset0/
  train.parquet
  test.parquet
  source_rows.jsonl
  dataset_summary.json
```

- 启动训练时设置 `SWE_PREPARE_DATA=0`，直接使用已生成 parquet。

后续建议：

- 将 prepare 阶段移入容器执行；或
- 为 7142 宿主机配置固定 Python venv；或
- 在训练脚本中显式检测 pandas/pyarrow 并给出可操作错误。

### 11. VeRL batch size 不能小于并行最小约束

现象：

尝试 `TRAIN_BATCH_SIZE=1` 跑 1 sample smoke 时 VeRL 报：

```text
AssertionError:
real_train_batch_size (1) must be divisible by minimal possible batch size (8)
```

根因：

当前 8 GPU / rollout TP 配置下，VeRL 校验要求真实 train batch size 可被最小并行 batch size 8 整除。

处理：

使用：

```text
TRAIN_BATCH_SIZE=8
PPO_MINI_BATCH_SIZE=8
ROLLOUT_N=1
LIMIT=8
```

完成 1-step 真实 GRPO smoke。

### 12. 208.77 LLM 隧道指向错误端口

现象：

真实 OpenHands rollout 初次尝试失败：

```text
Connection reset by peer
```

根因：

208.77 LLM config 指向：

```text
http://127.0.0.1:18199/v1
```

但 SSH 隧道当时转到 7142 `18888`，而 18888 gateway 后端 `127.0.0.1:8000` 未监听，返回 `backend_starting` 或连接重置。正式训练时 VeRL 自己拉起的 model gateway 端口是 `18088`。

修复：

将 208.77 隧道改为：

```text
127.0.0.1:18199 -> 7142:18088
```

验证：

训练中 7142 `18088` ready 后，208.77 访问：

```text
GET http://127.0.0.1:18199/v1/models
```

可返回 Qwen3.6-35B-A3B model list。
