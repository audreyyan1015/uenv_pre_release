# 百卡 / 千卡仿真环境服务系统 — 稳定性指标方案

> 日期：2026-07-22
> 范围：基于当前 UEnv Episode Stack（Bridge → Server → Worker → Plugin / SWE Runtime / Model Gateway），为后续 **百卡、千卡级多卡仿真环境压测与联调** 提供统一、可落地的稳定性评估标准
> 关联文档：[大规模演进方案](../../older/uenv-scale-evolution-plan.md)、[Worker Pool 层设计](../../older/worker-pool-layer-design.md)、[OlymMATH 长耗时连接问题](../260716/OlymMATH长耗时Episode连接问题说明.md)、[Worker 插件生命周期与资源回收](../../debug_log/20260717-Worker插件实例生命周期与资源回收改进方案.md)、[术语规范](./Math环境与术语规范-可证明性与DSCode-Agent选型.md)

## 1. 目标与使用方式

### 1.1 要解决的问题

后续多卡仿真环境测试需要回答同一类问题：

> 「在目标并发与时长下，**环境服务系统本身**是否稳定？」

若把模型答错、SWE 未 resolve、harness wrong_answer 等**任务能力结果**混进稳定性分母，会导致：

- 无法区分「平台挂了」与「模型没做对」；
- 百卡 / 千卡扩容后无法横向对比；
- 回归时缺少统一通过线。

本方案给出一组**详细指标 + 分级门槛 + 报告口径**，作为后续所有百卡 / 千卡仿真稳定性测试的**统一评估标准**。

### 1.2 评估对象（本方案只评这些）

| 纳入稳定性评估 | 不纳入稳定性主分（另报能力轨） |
|----------------|--------------------------------|
| Episode 能否被可靠调度、执行、回报 | `reward`、`pass@1`、`resolved` |
| gRPC / 控制面连接是否持续可用 | 答案正确性、patch 质量 |
| Worker / 插件 / 容器资源是否可回收 | 模型吞吐优化（除「推理侧拖垮平台」外） |
| 排队、超时、重试是否受控 | Benchmark 官方分数对齐 |

术语对齐：评的是 **Episode Stack（环境执行平台）稳定性**，不是 Task Environment 判分能力，也不是 Agent 策略水平。见 [术语规范](./Math环境与术语规范-可证明性与DSCode-Agent选型.md) §4。

### 1.3 规模定义（本仓库口径）

| 档位 | 含义（仿真环境侧） | 典型并发锚点 | 说明 |
|------|--------------------|--------------|------|
| **百卡级** | 约 **100 张训练/推理 GPU** 对应的仿真吞吐目标 | 并发 Episode ≈ **64～512**（参考已有压测：64 Worker × 8 = 512） | Phase 1 目标；单 Region、单 Server 控制面仍可行 |
| **千卡级** | 约 **1000 张 GPU** 对应的仿真吞吐目标 | 并发 Episode ≈ **1k～8k** 量级；Worker 数百～千台 | 需 Region 分层、指标推送聚合；见规模演进 Phase 2+ |

> **注意**：UEnv 中 GPU 主要在 **推理 / vLLM / 训练 Actor**；Worker 侧多为 CPU 进程或 SWE 容器。稳定性指标以 **Episode 并发与 Worker 节点数** 为直接自变量，「卡数」通过「目标训练吞吐所需的并行 Episode」换算，不在 Worker 上强行绑死 1 Episode = 1 GPU。

### 1.4 文档产物约定

每次百卡 / 千卡稳定性试验，至少产出一份报告，包含：

1. **试验剖面**：档位、时长、`env_type` 组合、并发、超时、重试配置；
2. **核心稳定性得分卡**（§7）；
3. **分维度明细表**（§3～§6）；
4. **失败归因 Top-N**（按 `error_code` / 相位 / 传输类）；
5. **与门槛对照的结论**：通过 / 有条件通过 / 不通过。

## 2. 评估原则

### 2.1 四条硬原则

1. **稳定性与能力分轨**
   - **稳定性失败**：传输中断、无可用 Worker、lease/epoch、插件崩溃、队列超时、超过 `max_attempts` 的平台侧失败、资源耗尽等。
   - **能力失败**：`wrong_answer`、SWE unresolved、reward=0 但 Episode `completed`。
   - 能力失败**不计入**稳定性失败率分母中的「失败」；可单独报「任务成功率」。

2. **按相位归因，禁止只报一个 error_count**
   至少区分：`admission` → `dispatch` → `acquire/reset` → `model_callback` → `env.step` → `report/wal` → `release`。

3. **终态看 Final Attempt，过程看 Attempt 膨胀**
   - 终态成功率看最终 `EpisodeResult`；
   - 同时要求 `attempts / episodes` 接近 1，避免「靠重试刷绿」。

4. **长稳与尖峰分开报**
   - **稳态试验**：固定并发、持续 T 小时；
   - **尖峰试验**：阶梯加压 / 突发提交；
   - 不可用单一短时 smoke 代替长稳结论。

### 2.2 与现有可观测性的关系

| 已有底座 | 路径 | 本方案用法 |
|----------|------|------------|
| Worker Prometheus | `uenv-worker/src/metrics.rs`，`GET /metrics` | 吞吐、池状态、心跳滞后、WAL |
| Server Admin | `GET /health`、`/status`、`/agents` | Worker healthy/degraded、在途负载 |
| 轨迹服务 | `uenv_trajectory_*` | 上传成功率、冲突/孤儿 |
| Hub | `uenv_hub_http_*` | 冷路径（扩缩容期），不进热路径主分 |
| Bridge 评测 `metrics.json` | 各 `evaluate_*_uenv.py` | 稳定性失败与能力失败拆分口径 |

**已知缺口（试验中需补齐采集，即便尚未落 Prometheus）**：

- Server 主路径：admission 等待、dispatch 失败、attempt 原因、degraded 计数；
- gRPC transport 分类：`CANCEL` / `broken pipe` / 静默无帧；
- 插件 OS 进程数与 Warmup 池对账差；
- Model Gateway 在途数 / 5xx / 排队深度。

指标未落库前，允许用 **结构化日志聚合 + 试验脚本汇总** 作为等价数据源，但报告须注明数据来源与采样窗口。

### 2.3 稳定性失败判定表（统一标签）

| 标签 `stability_class` | 判定条件（示例） | 是否计稳定性失败 |
|------------------------|------------------|------------------|
| `ok_completed` | `status=completed`，无论 reward | 否 |
| `ok_failed_task` | 业务上「做错了」但环境完整跑完并回报 | 否（能力轨） |
| `stab_transport` | gRPC CANCEL、broken pipe、stream 无心跳后断连 | 是 |
| `stab_capacity` | `ERR_NO_AVAILABLE_WORKER`、admission/queue timeout、acquire semaphore timeout | 是 |
| `stab_worker` | Worker degraded/假活、crash、lease/epoch 拒绝导致任务不可达 | 是 |
| `stab_env` | 插件崩溃、环境 reset/step 非确定性基础设施故障（非 wrong_answer） | 是 |
| `stab_model_infra` | Model Gateway/vLLM **不可达、超时、5xx 拖垮 Episode**（非「模型答错」） | 是 |
| `stab_timeout` | `ERR_EPISODE_TIMEOUT` / `ERR_WORKER_TIMEOUT`（平台超时） | 是 |
| `stab_exhausted` | `exceeded max attempts` 且历次 attempt 均为上述稳定性类 | 是 |
| `stab_resource` | 进程泄漏、磁盘满、OOM、容器耗尽导致不可服务 | 是 |

> 若某次失败无法归类，记 `stab_unknown`，**按稳定性失败计**，并强制人工复核。

## 3. 核心稳定性指标（一级指标，必报）

以下指标构成**统一得分卡**的主干。所有百卡 / 千卡试验必须给出数值与门槛对照。

### 3.1 可用性与成功率

| ID | 指标名称 | 定义 | 单位 | 采集建议 |
|----|----------|------|------|----------|
| **S1** | **Episode 终态完成率** | `N(ok_completed ∪ ok_failed_task) / N(submitted)` | % | Bridge / Server 终态聚合 |
| **S2** | **平台稳定性成功率** | `1 - N(stability_class ∈ stab_*) / N(submitted)` | % | 按 §2.3 打标 |
| **S3** | **服务可用时间占比（Availability）** | 试验窗口内，控制面可接受 Submit 且至少 1 个健康 Worker 可调度的时间占比 | % | Server `/status` 采样（建议 ≤15s） |
| **S4** | **无可用 Worker 比率** | `N(ERR_NO_AVAILABLE_WORKER 终态) / N(submitted)` | % | Server / Bridge |
| **S5** | **超时终态率** | `N(stab_timeout) / N(submitted)` | % | 终态 `error_code` |

**说明**：S1 ≥ S2；S1 含「跑完但答错」，S2 只关心平台是否可靠。对外说「环境服务稳定」时，以 **S2 + S3** 为准。

### 3.2 延迟与排队（SLO 型）

按 `env_type` 分桶报告（`math` / `code` / `swe` 不可混桶）。

| ID | 指标名称 | 定义 | 单位 |
|----|----------|------|------|
| **L1** | **Submit→首帧 StreamReport 延迟** | 从 Server 发起 Dispatch 到收到首个进度/心跳帧 | ms，报 p50/p95/p99 |
| **L2** | **Admission 等待时间** | Submit 进入到获得 admission permit | ms，p50/p95/p99 |
| **L3** | **Episode 端到端时延** | Submit→最终 EpisodeResult（含重试则取终态墙钟） | s，p50/p95/p99 |
| **L4** | **队列超时率** | admission / in-flight 等待超过配置上限的比例 | % |
| **L5** | **调度空转率** | 有待调度任务但连续 ≥X 秒无成功 Dispatch 的窗口占比 | % |

> 长思考任务（如 OlymMATH）L3 会自然偏大；**稳定性判据重点看 L1/L2/L4/L5 与传输类失败**，避免用「绝对耗时短」误杀合法长 Episode。

### 3.3 重试与幂等健康度

| ID | 指标名称 | 定义 | 单位 | 健康含义 |
|----|----------|------|------|----------|
| **R1** | **Attempt 膨胀比** | `Σ attempts / N(submitted)` | 倍 | 理想 ≈ 1.0～1.05 |
| **R2** | **首次成功占比** | 第 1 次 attempt 即终态成功（含能力失败）的比例 | % | 越高越好 |
| **R3** | **重试有效率** | 重试后由失败转成功的次数 / 总重试次数 | % | 过低说明在重试确定性失败 |
| **R4** | **确定性失败被重试比率** | 应禁止重试的 `env.step` 类失败仍被 Server 消耗 attempt 的比例 | % | 目标 → 0 |
| **R5** | **ReportResult 幂等冲突率** | duplicate / conflict / 非幂等错误占比 | % | 轨迹与结果双写一致性 |

### 3.4 控制面与连接稳定性

| ID | 指标名称 | 定义 | 单位 |
|----|----------|------|------|
| **C1** | **Worker 健康占比** | `N(healthy) / N(registered)` 时间平均 | % |
| **C2** | **假活检出有效率** | degraded 判定后，该 Worker 上新 Dispatch 成功率相对健康 Worker 的比值；或「假活未检出导致的连续失败簇」次数 | 次 / % |
| **C3** | **心跳滞后** | `uenv_heartbeat_lag_ms` 的 p95/p99；以及超阈值比例 | ms / % |
| **C4** | **gRPC 传输错误率** | transport 错误 Episode / 全部 Episode（按方向：S→W / W→S） | % |
| **C5** | **长连接存活达标率** | 对「预期墙钟 > T」的 Episode，stream 在完成前保持可写可读的比例 | % |
| **C6** | **重注册拒绝率** | `register_rejected`（lease/epoch）/ 重注册尝试次数 | % |
| **C7** | **Stream 静默间隔越界率** | 两帧 StreamReport 间隔超过防 CANCEL 心跳阈值的比例 | % |

### 3.5 资源与泄漏（百卡必测，千卡加重）

| ID | 指标名称 | 定义 | 单位 |
|----|----------|------|------|
| **P1** | **池对账误差** | `|OS 插件进程数 − Σ pool_size(warm/active/idle/…)|` 相对误差 | 个 / % |
| **P2** | **Warmup 命中率** | `hit / (hit+miss)` | % |
| **P3** | **Acquire 超时率** | 并发 semaphore / 池获取超时占比 | % |
| **P4** | **Worker RSS / FD 漂移** | 试验始末相对增长；或单位时间增长率 | MB、个、%/h |
| **P5** | **孤儿进程累计** | 试验结束时无法归属池状态机的插件/runtime 进程数 | 个 |
| **P6** | **SWE 容器对账** | 存活容器数 vs `uenv_swe_instance_pool_size` / gateway in-use | 个 |
| **P7** | **磁盘与 WAL 积压** | `uenv_wal_pending_records` p95；磁盘使用增长率 | 条、%/h |
| **P8** | **节点不可服务事件** | 因 OOM / 盘满 / PID 耗尽导致 Worker 退出或 degraded 的次数 | 次 |

### 3.6 推理侧基础设施（仅平台视角）

| ID | 指标名称 | 定义 | 单位 |
|----|----------|------|------|
| **M1** | **Model 回调基础设施失败率** | Gateway/vLLM 不可达、超时、5xx 导致的 Episode 稳定性失败占比 | % |
| **M2** | **Gateway 在途饱和时间占比** | `inflight ≥ 配置上限` 的时间占比 | % |
| **M3** | **Model 回调时延** | `model_callback` p50/p95/p99（已有 sum，试验需分位数） | ms |
| **M4** | **推理侧拖垮平台事件** | 因模型侧阻塞导致 Worker active 打满、假活或大规模 timeout 的事件数 | 次 |

> 模型 **答错** 不进 M1；仅「调用链路本身坏了」才算。

## 4. 二级指标（分场景加深，建议报）

### 4.1 按 `env_type` 的场景指标

| 场景 | 额外必选指标 | 原因 |
|------|--------------|------|
| **math**（含长 thinking） | C5、C7、L1；长 Episode（>60s）子集的 transport 失败率 | 已证实 HTTP/2 CANCEL / broken pipe |
| **code**（DSCode harness） | harness 进程超时 vs 平台超时拆分；依赖缺失导致的 `stab_env` 比率 | 避免把缺库当成模型差 |
| **swe**（Agent + Docker） | Runtime Gateway 利用率、容器创建失败率、Agent 池排队、轨迹上传 S/R5 | 容器与 Agent 是独立容量维度 |

### 4.2 吞吐与效率

| ID | 指标名称 | 定义 |
|----|----------|------|
| **T1** | **稳态 Episode 吞吐** | 成功终态（S1 口径）Episode / 分钟 |
| **T2** | **有效算力利用率** | `Σ episode_active_time / (N_workers × max_concurrent × wall_time)` |
| **T3** | **调度损耗比** | `(L2 + Dispatch RTT) / L3` 的 p95 |
| **T4** | **容量达成率** | 实际稳态吞吐 / 理论容量（`Σ max_concurrent` × 单 Episode 期望速率） |

### 4.3 故障注入与恢复（千卡试验建议必做子集）

| ID | 指标名称 | 定义 |
|----|----------|------|
| **F1** | **Worker 宕机恢复时间（MTTR）** | 从进程退出到替代容量重新可调度 |
| **F2** | **滚动升级无中断窗口** | 升级期间 S2 不低于门槛的时长占比 |
| **F3** | **脑裂/双注册收敛时间** | 重复 endpoint / epoch 冲突到只剩一个有效注册 |
| **F4** | **WAL 重放成功率** | 断连后本地 WAL 记录成功 Report 的比例 |
| **F5** | **Server 重启后状态可恢复度** | 重启后在途任务可解释比例（完成/失败/需重放）；内存态丢失须显式记为风险项 |

### 4.4 冷路径（扩缩容期，不进热路径主分，但千卡必测）

| ID | 指标名称 | 定义 |
|----|----------|------|
| **H1** | **Hub 制品就绪时延** | `env sync` / 镜像 load 到 Worker 可服务 |
| **H2** | **同时扩容冲突率** | 批量 Worker 启动时 Hub 5xx / 超时比例 |
| **H3** | **镜像缓存命中率** | 本地已有镜像避免重复拉取的比例 |

## 5. 试验剖面（如何测才有资格谈指标）

### 5.1 标准试验矩阵

| 剖面 ID | 档位 | 时长 | 并发模型 | `env_type` | 目的 |
|---------|------|------|----------|------------|------|
| **B-Steady** | 百卡 | ≥ 2 h | 固定并发 = 目标容量的 70%～85% | math 为主 + code 抽样 | 稳态 S2/S3/P* |
| **B-Spike** | 百卡 | ≥ 30 min | 阶梯升至 100%→110% 容量 | math | 背压与 L4/L5 |
| **B-LongTail** | 百卡 | ≥ 1 h | 中并发 + 强制长输出/长 step | math/olymmath 类 | C4/C5/C7 |
| **B-Mixed** | 百卡 | ≥ 2 h | 混合 math:code:swe = 约定比例 | 三环境 | 干扰与资源隔离 |
| **K-Steady** | 千卡 | ≥ 4 h | 分区多 Region 或等价代理负载 | 以 math/code 为主 | 分层调度与指标聚合 |
| **K-Failure** | 千卡 | ≥ 1 h | 稳态中注入 Worker/网关故障 | 混合 | F1～F4 |
| **K-ColdStart** | 千卡 | 单次 | 批量上线 N Worker | — | H1～H3 |

未跑满对应档位的最短时长与剖面，**不得宣称该档位稳定性达标**。

### 5.2 试验必须固定并记录的配置项

- Server：`queue_dynamic` / `queue_max_in_flight`、`max_attempts`、`heartbeat_timeout_secs`、`worker_degraded_threshold_secs`、`broadcast_capacity`
- Worker：`max_concurrent`、`warmup_size`、`max_idle_time`、WAL 路径
- SWE：`runtime_gateway.capacity`、Agent 池上限
- 模型：Gateway 地址、超时、最大并发、TP/实例数
- 客户端：提交速率、总 Episode 数、是否允许客户端侧重试

### 5.3 对照基线

建议始终保留一组 **小规模金标**（例如单 Worker、并发 4、时长 30 min），用于确认「指标采集与打标逻辑」本身正确；大规模异常时先对比金标是否也漂。

## 6. 统一门槛（评估标准）

门槛分 **通过 / 有条件通过 / 不通过**。有条件通过必须附带缺陷单与复测计划。

### 6.1 百卡级门槛（B-* 剖面综合）

| 指标 | 通过 | 有条件通过 | 不通过 |
|------|------|------------|--------|
| **S2 平台稳定性成功率** | ≥ **99.0%** | 98.0%～99.0% | < 98.0% |
| **S3 可用时间占比** | ≥ **99.5%** | 99.0%～99.5% | < 99.0% |
| **S4 无可用 Worker 率** | ≤ **0.1%** | ≤ 0.5% | > 0.5% |
| **S5 平台超时率** | ≤ **0.5%** | ≤ 1.0% | > 1.0% |
| **R1 Attempt 膨胀比** | ≤ **1.05** | ≤ 1.15 | > 1.15 |
| **R4 确定性失败被重试率** | ≤ **0.1%** | ≤ 1.0% | > 1.0% |
| **C1 Worker 健康占比** | ≥ **98%** | ≥ 95% | < 95% |
| **C4 传输错误率** | ≤ **0.3%** | ≤ 1.0% | > 1.0% |
| **C5 长连接存活达标率**（长尾子集） | ≥ **99%** | ≥ 97% | < 97% |
| **P1 池对账误差** | ≤ **2 个/节点** 且相对误差 ≤ 1% | ≤ 5 个/节点 | 持续增长或 >5 |
| **P5 孤儿进程** | **0**（试验结束） | ≤ 3 且已定位 | 持续增长 |
| **P8 节点不可服务事件** | **0** | ≤ 1 且自动恢复 | ≥ 2 或未恢复 |
| **M1 推理基础设施失败率** | ≤ **0.5%** | ≤ 1.0% | > 1.0% |
| **L4 队列超时率** | ≤ **0.1%** | ≤ 0.5% | > 0.5% |

**综合判定规则（百卡）**：

- **通过**：S2、S3、C4、P5、P8 全部落在「通过」列，且其余指标无「不通过」。
- **有条件通过**：无「不通过」项，但存在 ≥1 个「有条件通过」项。
- **不通过**：任一项落在「不通过」，或 S2/S3/P8 任一不通过。

### 6.2 千卡级门槛（K-* 剖面综合）

在百卡门槛基础上收紧或增加：

| 指标 | 通过 | 有条件通过 | 不通过 |
|------|------|------------|--------|
| **S2** | ≥ **99.5%** | 99.0%～99.5% | < 99.0% |
| **S3** | ≥ **99.9%** | 99.5%～99.9% | < 99.5% |
| **C4** | ≤ **0.1%** | ≤ 0.3% | > 0.3% |
| **R1** | ≤ **1.03** | ≤ 1.08 | > 1.08 |
| **T4 容量达成率**（稳态） | ≥ **80%** | ≥ 70% | < 70% |
| **F1 MTTR（Worker）** | ≤ **3 min** | ≤ 10 min | > 10 min |
| **F4 WAL 重放成功率** | ≥ **99.9%** | ≥ 99.0% | < 99.0% |
| **指标管道可用性** | Push/聚合失败率 ≤ **0.1%** | ≤ 1% | > 1% 或大面积盲区 |

**千卡额外否决项（一票否决）**：

1. 控制面单点故障导致全局不可提交超过 **5 分钟**；
2. 指标大面积缺失导致无法复核 S2（「看不见就不算过」）；
3. 资源泄漏导致 ≥ **1%** Worker 在 4h 内进入不可服务。

### 6.3 分级评分卡（可选，便于横向对比）

将一级指标映射为 0～100 分，便于多轮试验对比：

| 维度 | 权重 | 组成 |
|------|------|------|
| 可用性 | 30% | S2、S3、S4 |
| 连接与控制面 | 25% | C1、C4、C5、C7 |
| 资源健康 | 20% | P1、P5、P7、P8 |
| 排队与重试 | 15% | L4、R1、R4 |
| 推理基础设施 | 10% | M1、M2 |

**分数换算**：该维度内各指标按「通过=满分、有条件=60%、不通过=0」线性插值后加权。
**建议对外口径**：同时给出 **通过/有条件/不通过** 与 **总分**；争议时以门槛表为准，不以总分代替否决项。

## 9. 明确不作为稳定性主指标的内容

以下内容**可以**出现在同一试验的附录，但**不得**用于判定「环境服务是否稳定」：

| 内容 | 原因 |
|------|------|
| `reward` / `pass@1` / SWE `resolved` | 能力轨 |
| 仅模型侧 token/s、TTFT 优化数字 | 除非触发 M1/M4 |
| Hub 功能完整性（非扩容试验） | 非 Episode 热路径 |
| 前端可视化是否美观 | 与服务稳定性无关 |
| 单次 smoke 3 条 Episode | 样本不足，不能代替 B-Steady |
