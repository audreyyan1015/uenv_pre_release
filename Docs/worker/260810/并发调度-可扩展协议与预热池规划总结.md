# 并发调度、可扩展协议与预热池规划总结

日期：2026-08-10

## 0. 精简结论

当前并发调度策略已经形成可运行闭环：Worker 侧服务器通过本地配置和运行时能力探测上报 `max_concurrent`、支持的 `env_type`、EnvPackage 状态、pool snapshot 等信息，Server 根据这些上报结果做 admission、reserve 和 dispatch。后续在 ToolPackage / RuntimeProfile / 分布式工具调用封装落地后，Server 可以把环境实例、工具服务、Agent job、artifact/reward runner 都看成可租约资源，并基于历史累计数据预测新拉起环境或 agent 实例的资源开销，从而更精细地利用多台服务器的 CPU、内存、磁盘、容器槽位和外部工具容量。

当前已引入的代码脚手架和协议扩展方向，核心目标是把 reward 计算、轨迹保存、路由、环境语义切换等差异从框架核心代码中剥离出来。默认支持的 `qa`、`code`、`swe` 等环境会继续提供默认模板和默认 contract；后续新增或修改环境时，应优先通过 EnvPackage 的 `worker_overlay`、`agent_defaults`、`contracts`、`interface`、artifact 和 Episode Stack 等字段声明接入，而不是在 Server / Worker / Adapter 中增加新的硬编码分支。

当前通用 WarmupPool 与 SWE 所需预热池存在语义差异：通用 WarmupPool 主要服务 `qa/code` 这类 process plugin，按 `env_type` 预热本地进程槽；SWE 则需要 Runtime Gateway、Docker workspace、benchmark variant、patch 方向、trajectory seal、官方 reward adapter 和 agent scaffold 协同，不能直接塞进同一个池模型。短期需要新增并统一暴露 SWE 预热池账本；长期随着浏览器、数据库、GPU grader、真实设备等环境类型引入，其他自定义环境也可能需要扩展专属 pool 或 ToolPackage pool，但应通过统一 RuntimeProfile 和 lease 协议接入。

## 1. 并发调度策略现状与后续规划

### 1.1 当前检查结论

目前调度链路不是由 Adapter 单侧决定，也不是 Server 静态写死某台机器容量，而是由 Worker 侧运行时上报能力，Server 根据上报状态动态调度：

- Worker 配置 `worker.max_concurrent`，注册和心跳时上报容量。
- Worker 上报 `supported_env_types`、`platform_features`、`backend_kinds`、`trajectory_schemas`、`tool_schemas`。
- Worker 上报已同步或已准备的 EnvPackage 状态，例如 `swe-bench-pro@0.3.4`、`swe-bench-smith@0.1.0-local`。
- Worker 对通用 process plugin 暴露 `pool_summary` / `pool_slots`，前端和 Server admin 可看到 ready、busy、warming 等状态。
- Server admission 可跟随 Worker 动态容量调整，Scheduler reserve 时按 `env_type`、EnvPackage、资源状态、drain/degraded 状态和 load/capacity 做过滤。

当前链路已经可以并发推进 episode：

```text
VeRL rollout / batch
  -> Adapter ExecuteBatch
  -> Server admission
  -> Scheduler reserve Worker capacity
  -> Worker max_concurrent
  -> Worker pool / SWE Runtime Gateway / AgentJob
  -> EpisodeResult + trajectory + reward
```

本轮文档和实机检查确认的主要问题不是“完全不能并发”，而是并发策略仍然分散在多层配置中：Adapter 的 batch size、Server admission、Worker `max_concurrent`、Runtime Gateway capacity、AgentRegistry capacity、WarmupPool 目标值分别存在，训练 run 还缺少一个端到端显式声明的调度策略。

### 1.2 已完成或已规划的协议调整

260807 的调度梳理中已经明确第一阶段应补齐 run / batch 级 `SchedulingPolicy`，包括：

- `max_episode_concurrency`：本次 run 或 batch 同时推进的 episode 上限。
- `max_in_flight_batches`：避免多个 batch 叠加把 Worker 池占满。
- `target_worker_slots` / `pool_warmup_target`：希望 Worker 准备的 warm slots。
- `max_parallel_per_worker`：限制单 Worker 对同一 run 或 env_type 的并行占用。
- `agent_job_max_concurrency`：Agent 侧可承接的并发 job 上限。
- `runtime_gateway_session_limit`：Gateway session 上限。
- `require_warm_slot`：是否要求有 ready slot 才 dispatch。

建议 Server 维护 `scheduling_group_id` 对应的 run/batch 级状态。每个 episode 先拿 group permit，再进入全局 admission 和 Worker reserve，完成、失败、取消或超时时统一释放 permit 和 Worker lease。

### 1.3 后续资源开销预测规划

在环境工具结构化和分布式工具调用封装落地后，Server 不应只看“Worker 还有几个空 slot”，而应按 RuntimeProfile 做多资源准入：

```text
EpisodeRequest
  -> resolve RuntimeProfile
  -> 预测 env / tool / agent / artifact / reward 资源开销
  -> acquire scheduling group permit
  -> acquire WorkerSlotLease
  -> acquire ToolLease / ToolSessionLease
  -> acquire AgentLease
  -> dispatch episode
  -> collect trajectory / artifact / reward
  -> release all leases
```

资源预测的初步规划如下：

- Worker 和 ToolService 持续上报历史运行数据，包括冷启动耗时、ready 命中率、CPU/内存峰值、磁盘占用、容器创建耗时、reward 执行耗时、artifact 上传大小、Agent job 时长。
- Server 按 `env_type + package_id + version + benchmark_variant + tool_profile + agent_kind` 聚合历史统计，形成 p50/p90/p99 成本画像。
- 新 episode 到达时，Server 使用历史画像估计新拉起 env instance、tool session 或 agent job 的成本。
- 调度时同时考虑当前 load、已保留 reservation、预计峰值资源、冷启动成本和 pending 队列，优先选择能最小化等待时间且不会挤爆资源的 Worker / ToolService。
- 对数据不足的新 EnvPackage 使用 manifest 中的 `resource_spec` 和保守默认值；运行足够多 episode 后自动用历史累计数据修正。

这样 Server 可以从“按 Worker 自报容量粗粒度调度”演进到“按预测成本和多资源 lease 动态调度”，在多机部署时更充分利用服务器资源。

## 2. 代码脚手架和可扩展协议

### 2.1 当前已经具备的基础

当前 Hub / Worker / Server 已经具备动态 EnvPackage 接入的第一阶段能力：

- Hub 中 EnvPackage 是版本化、内容寻址的分发单元，包含 artifacts、`worker_overlay`、`agent_defaults`、`contracts`、`interface` 等字段。
- Worker 可按 `env_type` 从 Hub 拉取 manifest，并把 `openenv_http` / `generic_openenv_plugin` / HTTP entrypoint 映射为本地 `plugins/{env_type}/run.sh`。
- `uenv-openenv-plugin` 已能把 OpenEnv HTTP 的 `/reset`、`/step`、`/close` 映射到现有 episode/reward/trajectory 结果。
- Server 在没有 ready Worker 时，可以选择具备 `hub_dynamic_env` 的 Worker 执行 prepare，然后重新 reserve / dispatch。
- 前端和 admin HTTP 已能显示 Worker capability、package states、trajectory/tool schemas 和实例池快照。

这意味着未知环境的首轮动态接入已经能跑通：Hub 注册、Worker prepare、Server 调度、episode 执行、reward 与 trajectory 返回、artifact URI 引用、前端可见。

### 2.2 默认环境类型和默认模板

当前默认支持的环境类型可按运行形态分为几类：

| 环境类型 | 默认定位 | 当前接入方式 |
|----------|----------|--------------|
| `qa` | 规则判分 / rubric / 数学与问答类验证环境 | process plugin / OpenEnv shim，按 dataset 路由 |
| `code` | 代码执行与单元测试类环境，例如 DSCodeBench | process plugin，沙箱执行 harness 后返回 reward |
| `swe` | SWE-bench Pro / SWE-smith 这类仓库级软件工程环境 | Runtime Gateway + `SweInstancePool` + Agent scaffold / native harness |
| 动态 OpenEnv HTTP 环境 | 用户自定义 reset/step/close HTTP 服务 | EnvPackage manifest 生成本地 shim，无需改核心代码 |

这些默认类型应继续提供默认脚手架模板：

- `qa` 模板：标准 action/observation/state schema、rubric 或 rule reward 配置、dataset 路由、trajectory v2.2 输出。
- `code` 模板：代码提取、测试 harness 调用、timeout、测试通过数解析、artifact 和 trajectory 输出。
- `swe` 模板：benchmark variant、workspace contract、patch/gold 方向、Runtime Gateway、Agent scaffold、官方 reward adapter、trajectory seal。
- `openenv_http` 模板：把用户 HTTP 服务适配到 UEnv reset/step/close 和 reward/trajectory 返回口径。

用户扩展环境时，不应直接修改 Server 调度代码或 Worker 核心执行代码。推荐把差异写入 EnvPackage：

- `worker_overlay`：声明 backend、env_type、benchmark variant、runtime contract、image pull policy、pool 默认值、reward adapter 环境变量名等。
- `agent_defaults`：声明默认 agent scaffold、agent_kind、工作目录、工具桥接默认参数。
- `contracts`：声明 Runtime Gateway API、trajectory bundle schema、tool bridge schema。
- `interface`：声明 OpenEnv-style action / observation / state schema。
- `artifacts`：声明 catalog、eval spec、镜像 tar、overlay、agent bridge、其他依赖制品及 digest。
- Episode Stack：把 task env、agent scaffold、Runtime Gateway 和 env packages 组合成可校验的运行栈。

### 2.3 Reward 计算协议

Reward 不应散落在 Adapter 或训练脚本里做特判。当前和规划中的模式包括：

- 平台通用 reward adapter：适合 rule reward、rubric scorer、测试通过数、diff/patch/compile/unit test 等可由平台统一执行的判分。
- EnvPackage 自带 reward endpoint：适合私有 grader、强业务逻辑或必须读取环境内部状态的评分。
- SWE runtime contract：SWE-bench Pro 和 SWE-smith 的 buggy 状态、gold patch 方向、workspace 路径、reward adapter 命令由 `BenchmarkRuntimeContract` 驱动，而不是由 Adapter 手写 Pro/Smith 特判。

后续新环境如果能通过 reward contract 表达输入、输出和执行位置，Worker 只需要校验 reward 结构并记录结果，不需要新增核心代码分支。

### 2.4 轨迹保存协议

轨迹保存应坚持“索引和摘要进 EpisodeResult，大文件进 artifact store”的原则：

- EpisodeResult 保存 trajectory id、checksum、schema、reward 摘要和 artifact URI。
- 浏览器 trace、HAR、截图、DOM dump、测试日志、patch、stdout/stderr 等大文件作为 artifact bundle 保存。
- trajectory / artifact / reward 输入必须携带 `episode_id`、tool session id、package digest 和 checksum，避免并发串线。
- Worker trajectory recorder 负责 seal 和 upload，失败应可观测，但不应无条件阻断 reward 返回，除非该环境 contract 明确要求轨迹为强一致产物。

### 2.5 路由和环境语义切换

路由层应保持两个原则：

- 顶层调度键使用稳定的 `env_type`，例如 `qa`、`code`、`swe`，不要把每个 benchmark 拆成新的顶层环境类型。
- benchmark、dataset、variant 和 runtime 语义通过 payload、EnvPackage、`worker_overlay` 或 Episode Stack 表达。

SWE 已经按这个原则收敛：`env_type` 仍然是 `swe`，SWE-bench Pro / SWE-smith 通过 `benchmark_variant` 和 runtime contract 区分。Adapter 侧只传递足够语义字段，不再负责 patch 方向、gold apply 方向或 reward adapter 选择。

## 3. 不同环境类型与预热池兼容

### 3.1 当前 WarmupPool 的语义

当前通用 WarmupPool 面向 process plugin 型环境，典型是 `qa`、`code` 和动态 OpenEnv shim。它的主要职责是：

- 按 `env_type` 准备本地 plugin 进程或 shim。
- 维护 ready/busy/warming slots。
- `acquire()` 优先使用 ready 实例，不足时按需 spawn。
- `fill_pool()` 根据 `warmup_size` 补齐 ready 水位。
- 通过 `snapshot()` 上报 `pool_summary` 和 `pool_slots`。

这个模型适合轻量、同构、生命周期相对简单的 reset/step 插件环境。

### 3.2 SWE 与通用 WarmupPool 的冲突

SWE 不能简单复用现有 WarmupPool，原因包括：

- SWE 实例不是单纯 plugin 进程，而是仓库级 Docker workspace / session。
- SWE Agent 模式需要 Runtime Gateway，把 Agent host 上的命令路由到 Worker 侧容器。
- SWE 需要按 `benchmark_variant` 分桶，Pro 和 Smith 的 catalog、镜像、patch 语义和 reward adapter 不同。
- SWE 的初始状态、gold patch 方向和 reward 方向由 runtime contract 决定，不能按普通 `env_type=swe` 一把梭。
- SWE session 与 Docker 容器、workspace、trajectory seal、artifact 上传、AgentJob lifecycle 存在 1:1 或强关联。
- 实机已经观察到 SWE 容器可运行且 metrics 有 `uenv_swe_instance_pool_size`，但通用 `pool_summary` / `pool_slots` 没有 SWE slot，说明它当前确实由独立 `SweInstancePool` 管理。

因此当前冲突不是命名问题，而是生命周期和资源模型不同：通用 WarmupPool 预热的是可复用插件槽，SWE 预热/租用的是带 repo、session、gateway 和语义 contract 的容器槽。

### 3.3 为什么需要新增 SWE 预热池

新增 SWE 预热池的目的不是再造一套不可见资源，而是把 `SweInstancePool` 纳入统一账本和调度视图：

- 对 Server：reserve 时可以看到 SWE 的 ready/busy/capacity，不再只凭 Worker 总 load 判断。
- 对 Worker：Gateway/native SWE 都必须通过同一 acquire/release，避免绕开池导致超卖或泄漏。
- 对 Agent：AgentJob capacity、Gateway session 和 SWE slot 可以用同一个 K 对齐。
- 对前端：Worker 详情页能看到 SWE package ready、SWE pool busy/ready 和 active session。
- 对运维：取消、失败、超时、Worker 重启后可以 reconcile 残留容器和孤儿 lease。

短期实现可以保留内部 `SweInstancePool`，对外投影成统一 `pool_summary` / `pool_slots`。长期应让 SWE pool、process plugin pool 和 ToolPackage pool 都通过 RuntimeProfile / lease 协议被 Server 统一调度。

### 3.4 后续其他环境是否需要新增预热池

后续新增环境是否需要专属预热池，取决于它的资源和生命周期是否能被通用 process plugin pool 表达。

通常无需新增专属池的情况：

- 轻量 HTTP / process reset-step 环境。
- 只需要本地脚本、规则判分、少量 artifact 输出。
- 可通过 `warmup_size`、`max_concurrent` 和普通 acquire/release 表达生命周期。

可能需要新增专属 pool 或 ToolPackage pool 的情况：

- 浏览器类环境：需要 Playwright/Chrome context、profile 隔离、HAR/trace/screenshot 采集。
- 数据库类环境：需要 per-episode schema、事务隔离或独占 DB 实例。
- GPU grader 或仿真器：启动成本高、资源独占、必须按 GPU/显存调度。
- 真实设备或商业 license 工具：并发受设备数或 license 数限制。
- 多容器 / K8s pod 环境：需要 sidecar、volume、网络策略和 pod lifecycle。
- SWE 类仓库环境：需要 workspace、patch、Gateway、Agent scaffold 和官方 harness 协同。

这些环境不一定都要像 SWE 一样新增硬编码池。更推荐的演进方向是引入 ToolPackage：

```text
Thin Env Session
  + ToolPackage pool(browser / grader / artifact / db / proxy)
  + Agent job pool
  + Server Resource Broker
```

也就是说，专属池应逐步从“某个 env_type 的特殊代码”演进为“某个 RuntimeProfile 声明的可租约资源”。

## 4. 当前默认支持与自定义环境引入方式

当前默认支持的主线环境类型是：

- `qa`：规则验证、rubric、数学/问答类任务。
- `code`：代码执行、单元测试、DSCodeBench 类任务。
- `swe`：仓库级软件工程任务，包括 SWE-bench Pro / SWE-smith。
- `openenv_http` / `generic_openenv_plugin`：用户自定义 OpenEnv HTTP 服务动态接入。

自定义环境推荐按以下路径引入：

1. 在 Hub 注册 Task Environment，声明稳定 `env_type`、schema、dataset 或 config 约束。
2. 发布 EnvPackage，包含 catalog、eval spec、镜像或脚本、worker overlay、agent defaults、contracts、interface。
3. 如需要外部工具，声明 ToolPackage 依赖和资源模型；当前阶段可先以 Worker 本地 sidecar 或 process 方式落地。
4. 如需要 Agent，发布 Agent scaffold，并通过 Episode Stack 把 task env、agent scaffold、Runtime Gateway 和 env packages 固定为一个可解析组合。
5. Worker prepare 时拉取 EnvPackage / ToolPackage，更新 supported env types、package states 和 pool snapshot。
6. Server 根据 RuntimeProfile、Worker capability 和 scheduling policy 做准入与 dispatch。
7. EpisodeResult 按统一 reward、trajectory、artifact 协议返回。

这条路径的目标是：新增环境主要新增 manifest、模板、制品和可选 ToolPackage，而不是修改 Server / Worker 核心调度代码。

## 5. 环境依赖解耦的增量方案

### 5.1 解耦目标

先前讨论的核心判断是：EnvPackage 不应继续承担“环境本体 + 浏览器 + reward runner + trajectory recorder + artifact uploader + agent 工具桥 + 外部服务依赖”的全部职责。否则每新增一个环境，就容易出现以下问题：

- 同一套浏览器、数据库、grader、artifact 上传器被重复打进多个环境镜像。
- 为了提高并发，只能复制完整大环境实例，冷启动和磁盘成本随并发线性放大。
- Worker / Server 需要按 env_type 增加特殊分支，后续环境越多，核心调度越难维护。
- reward、trajectory、工具 session 和 artifact 的并发隔离只能靠环境内部自觉实现，平台侧难以统一审计和回收。

目标形态应改为：

```text
EnvPackage
  描述环境本体、接口、schema、默认依赖引用

ToolPackage
  描述可复用工具、sidecar、runner、service、session 和资源模型

RuntimeProfile
  解析 EnvPackage + ToolPackage + Agent scaffold 后得到一次 episode 需要的完整运行栈

Server / Resource Broker
  按 RuntimeProfile 申请 env、tool、agent、artifact、reward 等租约
```

也就是说，EnvPackage 负责“这个任务环境是什么、怎么 reset/step/score、需要哪些能力”；ToolPackage 负责“这些能力如何安装、启动、池化、暴露、限流、回收”；RuntimeProfile 负责把二者组合成调度器可以理解的资源声明。

### 5.2 EnvPackage 的边界

EnvPackage 应保留环境语义和接入契约：

- `env_type`、EnvPackage id/version/digest。
- process、OpenEnv HTTP、container、SWE runtime contract 等环境入口。
- action / observation / state schema。
- env config schema、dataset/catalog、benchmark variant。
- artifact layout、trajectory schema、reward contract。
- 默认 agent scaffold、默认 tool dependency 引用。
- 需要的 Worker feature，例如 `hub_dynamic_env`、`generic_openenv_plugin`、`runtime_gateway_v1`、`trajectory_v2_2`。

EnvPackage 不应直接替换 Server 调度、Worker sandbox、trajectory indexer、全局 reward 汇总或 Worker 核心生命周期管理。环境可以带自己的 scorer、脚本、镜像和私有 endpoint，但必须通过 manifest / contract 声明输入输出，让平台能够统一校验、记录、限流和回收。

### 5.3 ToolPackage 的边界

ToolPackage 用于承载可复用的配套能力，典型类型包括：

| ToolPackage 类型 | 示例 | 主要职责 |
|------------------|------|----------|
| 浏览器工具 | Playwright service、Chrome profile、HAR capture、DOM dump、screenshot | 提供 browser context/session，输出 trace bundle |
| 轨迹工具 | trace recorder、artifact bundler、seal/checksum、upload client | 采集、封包、上传、生成索引 |
| reward 工具 | grader runner、rubric scorer、test evaluator、patch evaluator | 按 reward contract 计算分数 |
| agent 工具 | Agent scaffold、tool bridge、driver entrypoint | 把 Agent action 路由到环境或工具 |
| 外部依赖服务 | DB、proxy、文件服务、license 工具、GPU grader、真实设备 | 提供有并发上限的共享资源 |

ToolPackage manifest 至少应表达：

```json
{
  "tool_id": "browser.playwright",
  "version": "1.0.0",
  "runtime": "worker_sidecar | process | container_pool | k8s_service",
  "api_schema": "uenv.tool.browser.v1",
  "session_model": "stateless | shared_readonly | leased | exclusive | pooled",
  "capabilities": ["trace", "har", "screenshot"],
  "resource_spec": {
    "cpu": 2,
    "memory_mb": 4096,
    "gpu": 0,
    "max_sessions_per_replica": 4
  },
  "pool": {
    "min_ready": 2,
    "max_replicas": 16,
    "queue_timeout_ms": 30000,
    "scale_metric": "pending_leases"
  },
  "healthcheck": {
    "path": "/health",
    "interval_ms": 5000
  },
  "artifacts": {
    "schema": "browser_trace_bundle_v1"
  }
}
```

这里的重点不是把工具改成远程 HTTP 服务，而是把工具变成可声明、可版本化、可租约、可池化、可观测、可回收的资源。某些工具可以是 Worker 本地 sidecar，某些可以是远端 ToolService，某些可以是 K8s Deployment / Job / Pod pool；Server 和 EnvPackage 不应依赖工具的具体部署位置。

### 5.4 RuntimeProfile 的组合语义

RuntimeProfile 是调度使用的最终形态。一个浏览器任务环境可解析成：

```json
{
  "env_type": "custom_browser_task",
  "env_package": "custom-browser-task@0.1.0",
  "backend": "openenv_http",
  "required_tools": [
    "browser.playwright@1",
    "trajectory.browser_bundle@1",
    "reward.env_endpoint@1"
  ],
  "worker_features": [
    "hub_dynamic_env",
    "tool_package_v1",
    "artifact_uri",
    "trajectory_v2_2"
  ],
  "pool": {
    "warmup_target": 4,
    "max_parallel_episodes": 4,
    "require_warm_slot": true
  },
  "agent": {
    "agent_kind": "openhands",
    "max_concurrent_jobs": 4
  }
}
```

Server reserve 时应使用 RuntimeProfile，而不是只看 `env_type`。同一个 `env_type` 在不同 package version、benchmark variant、tool profile、agent scaffold 下可能有完全不同的资源成本和并发能力。

## 6. 分布式工具封装后的并发调用方案

### 6.1 目标架构

后续封装分布式工具调用后，并行测试不应默认复制多个完整大环境实例，而应拆成 thin env session + 分布式工具运行时：

```text
Episode / Agent
  -> Thin Env Session
  -> Worker ToolProxy / Runtime Gateway
  -> Tool Router
  -> local sidecar / remote ToolService / K8s service / container pool
  -> artifact / trajectory / reward bundle
```

三层职责如下：

| 层 | 职责 | 示例 |
|----|------|------|
| Thin Env Session | 保留任务状态、reset/step/score 契约、workspace/session 隔离 | OpenEnv HTTP env、process plugin、轻量 sandbox |
| Distributed Tool Runtime | 承载可复用重型能力 | Playwright、grader、artifact uploader、trace recorder、DB/proxy |
| Resource Broker / Tool Scheduler | 为 episode 同时申请多类资源租约 | `WorkerSlotLease`、`ToolLease`、`ToolSessionLease`、`AgentLease` |

工具调用热路径不应每步都穿过 Server。Server 负责 resolve、准入、租约、审计和回收；Worker ToolProxy / Runtime Gateway 负责高频调用转发、session 校验、timeout、取消和本地观测。

### 6.2 多资源准入流程

并发 episode 进入系统时，准入流程应从单一 Worker slot 演进为多资源租约：

```text
EpisodeRequest
  -> resolve RuntimeProfile
  -> acquire scheduling group permit
  -> acquire WorkerSlotLease
  -> acquire required ToolLease / ToolSessionLease
  -> acquire AgentLease
  -> dispatch episode
  -> execute env/tool/agent/reward
  -> collect trajectory/artifacts
  -> release all leases
```

关键约束：

- Server 必须在 episode 开始前拿齐关键租约，避免运行中途才发现浏览器、DB、GPU grader 或 Agent job 不可用。
- `scheduling_group_id` 控制 run/batch 级并发，避免一个训练 run 把全部 ToolService 池占满。
- `WorkerSlotLease`、`ToolSessionLease`、`AgentLease` 之间需要补偿释放；任一 acquire 或 dispatch 失败都必须回滚已持有租约。
- 租约状态应进入 Server DB / Redis 等共享状态，支持 Server、Worker、ToolService 崩溃后的 orphan lease 回收。
- 心跳和 ToolService healthcheck 只提供 last-known 状态，调度防超卖仍应以 Server reservation + 池 busy 账本为准。

### 6.3 工具并发语义分类

不同工具不能统一按“无状态 HTTP 调用”处理。ToolPackage 需要声明 session model：

| session model | 示例 | 并发策略 |
|---------------|------|----------|
| `stateless` | schema validator、轻量 parser、format checker | 直接并发调用，按 QPS / CPU 限流 |
| `shared_readonly` | 只读数据集、镜像缓存、静态 fixture | 多 episode 共享，无需独占 session |
| `leased` | browser context、DB schema、workspace mount | 每个 episode 租一个 session，结束回收 |
| `exclusive` | GPU grader、真实设备、单 license 软件 | 独占 lease，其他 episode 排队 |
| `pooled` | Playwright browser、test runner、sandbox pod | 预热池 + pending leases 驱动扩缩容 |

因此工具解耦后的并发环境支持，核心不是“工具远程化”，而是让 Server 能知道每个工具的并发容量、隔离粒度、冷启动成本和回收方式。

### 6.4 浏览器轨迹环境示例

浏览器类环境可以按以下方式接入：

1. EnvPackage 声明 `required_tools = ["browser.playwright@1", "trajectory.browser_bundle@1"]`。
2. Worker prepare 时检查本机或远端 ToolService 是否已有对应 ToolPackage version。
3. 若缺失，Worker / ToolService 从 Hub 拉取 ToolPackage，启动 browser sidecar 或注册远端 endpoint。
4. Episode 开始时，Server 分配 `WorkerSlotLease` 和 `ToolSessionLease`。
5. Env / Agent 通过 Worker ToolProxy 调用浏览器能力，所有请求携带 `episode_id`、`lease_id`、`tool_session_id`。
6. ToolService 在 session 结束时输出 `trace.zip`、`network.har`、`screenshots/*.png`、`dom/*.json`、`tool-events.jsonl`。
7. Worker trajectory recorder 上传 artifact bundle，并在 EpisodeResult 中只写 trajectory id、checksum、schema、artifact URI 和 reward 摘要。

这类环境不要求浏览器与 env 容器同进程。浏览器可以是共享 sidecar，也可以是远端池化服务；只要 session 隔离、artifact 输出和 lease 回收满足 contract，EnvPackage 就不需要关心工具部署在哪里。

### 6.5 Reward 与 artifact 的并发隔离

Reward 计算同样应从环境本体中解耦出来：

- 平台通用 reward adapter 适合 rule reward、rubric scorer、测试通过数、patch diff、compile/unit test 等。
- EnvPackage 自带 `/score` 或私有 grader 适合必须读取环境内部状态的业务评分。
- GPU grader、商业 license grader、外部 API scorer 应作为 ToolPackage / ToolService 管理，并显式声明并发容量与排队策略。

所有 reward、trajectory、artifact 输入都应携带：

- `episode_id`
- `scheduling_group_id`
- `env_package_digest`
- `tool_package_digest`
- `tool_session_id`
- `lease_id`
- artifact checksum / size / schema

这组字段是并发环境支持的基本防串线条件。尤其在多 Worker、多 ToolService、多 Agent host 场景下，不能只靠路径命名或本地临时目录隔离。

## 7. 预热池与分布式工具池的关系

### 7.1 从完整实例池演进为多池组合

当前 WarmupPool 主要预热完整 process plugin；SWE 需要 `SweInstancePool` 管理容器/workspace/session。ToolPackage 落地后，预热池应进一步拆分：

```text
thin env pool
  + tool pool(browser / grader / artifact / proxy / db)
  + agent job pool
  + global resource broker
```

这并不意味着删除现有 WarmupPool。短期应保留现有池模型，并新增统一投影：

- process plugin pool 继续管理 `qa` / `code` / OpenEnv shim。
- SWE pool 内部继续用 `SweInstancePool`，对外投影 ready/busy/warming/capacity。
- ToolPackage pool 对外投影 ToolService replicas、ready sessions、busy sessions、pending leases、health。
- Server 统一按 RuntimeProfile 申请这些池中的 lease。

长期再把池抽象统一为“RuntimeProfile 声明的资源 provider”，而不是“某个 env_type 的特殊池”。

### 7.2 资源排队与扩缩容

ToolPackage pool 需要支持排队和扩缩容：

- `min_ready` 控制常驻预热容量。
- `max_replicas` 控制峰值成本。
- `queue_timeout_ms` 控制等待上限。
- `pending_leases`、queue wait p95、busy ratio、cold start p90 可作为扩容信号。
- idle TTL、低 busy ratio、长时间无 pending 可作为缩容信号。

Server 在选择 Worker / ToolService 时，应综合：

- Worker reported load 与 Server reservation。
- env pool ready/busy/warming。
- ToolService ready session / pending queue。
- AgentRegistry capacity。
- RuntimeProfile 的 p50/p90/p99 历史成本。
- 本次 run 的 SchedulingPolicy。

这与前文“资源开销预测规划”是一体的：历史画像越完整，Server 越能判断是复用 ready session、触发 prepare、等待已有 ToolService，还是把 episode 调度到另一台机器。

### 7.3 与现有 SWE 路径的收敛

SWE 当前是最接近“复杂环境 + Agent + Gateway + artifact/reward”的路径。它应作为统一模型的首个专用收敛对象：

| SWE 当前对象 | 统一模型中的位置 |
|--------------|------------------|
| `SweInstancePool` | `env_type=swe` 的 env pool provider |
| Runtime Gateway session | `ToolSessionLease` / `WorkerSlotLease` 的执行通道 |
| OpenHands AgentJob | `AgentLease` |
| benchmark variant | RuntimeProfile 的 variant / package 维度 |
| 官方 reward adapter | reward ToolPackage 或 EnvPackage reward contract |
| trajectory seal / artifact upload | trajectory ToolPackage / artifact bundle contract |

短期不要求把 SWE 全部改写成泛化 ToolPackage，但必须让它对外暴露同样的 pool snapshot、lease id、session id、artifact/reward contract。这样 Server 和前端才能用同一套视图看 process plugin、SWE、浏览器工具、DB 工具和未来 GPU grader。

### 7.4 实施优先级

建议按以下顺序推进：

1. 协议层补 `ToolPackageState`、`RuntimeProfile`、`PrepareToolPackage`、`ToolLease` / `ToolSessionLease`。
2. Worker 先支持本地 sidecar 型 ToolPackage，避免一开始就引入完整远端 ToolService 编排复杂度。
3. Server reserve 增加 RuntimeProfile resolve 和多租约回滚状态机。
4. 前端展示 Worker package states、env pool、tool pool、active sessions、pending leases。
5. 浏览器 trace / artifact bundle 作为第一类 ToolPackage 验证场景。
6. 再把远端 ToolService / K8s service / container pool 纳入相同协议。
7. 最后接入历史资源画像和预测调度，把 pool warmup target 从静态配置升级为按 run 和历史数据动态建议。

验收口径是：新增自定义环境时，用户主要提交 EnvPackage manifest、可选 ToolPackage manifest 和制品；Server / Worker 核心不新增 env_type 特判；并发 episode 能在多 Worker / 多 ToolService 上拿到独立 lease、独立 artifact、独立 reward，失败和取消后没有孤儿 session 或残留容器。

## 8. 需要继续跟进的事项

- 把 SWE `SweInstancePool` 的 ready/busy/session 状态合并进统一 pool snapshot。
- 让 Server reserve 对 SWE variant ready、Agent capacity、Gateway session limit 做统一判断。
- 建立 run/batch 级 `SchedulingPolicy` 状态和 `scheduling_group_id` semaphore。
- 完成 ToolPackage manifest、ToolService lifecycle、ToolLease / ToolSessionLease 和 RuntimeProfile resolve。
- 建立历史资源画像和预测调度：按 EnvPackage、ToolPackage、Agent scaffold、benchmark variant 聚合成本。
- 前端展示统一从 Worker package states、pool summary、tool states 和 active episodes 投影，不再依赖单一实例池来源。
