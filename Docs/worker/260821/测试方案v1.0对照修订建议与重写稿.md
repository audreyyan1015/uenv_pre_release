1. **多模态感知与交互能力**：仿真环境具备文本和结构化数据 **2** 种模态的感知与交互能力。

## 3. 测试内容与方法：参考范式差距 + 可达成重写

### 3.1 审计反馈对应的主要缺口

参考大纲（尤其课题二、泛睿、临床示范）的共同范式：

1. **用例列表**：序号 / 检测项 / 检测目标 / 用例编号
2. **单用例卡片**：前提条件、操作步骤（可逐步执行）、预期结果（可判定）
3. **指标—用例对应表**：考核指标 ↔ 用例编号
4. **性能/稳定性**：有明确阈值、采集方法、对比基线

当前 v1.0 §4 三项均停留在“验证能否… / 准备样例… / 判定：能够…”，**缺少可复现步骤与可量化阈值**，稳定性甚至“待协商后补充”——这正是审计方“测试方式要具体明确”的核心关切。**重点应改 §4，并补一张对应关系表。**

**（1）指标内容**
仿真环境具备文本和结构化数据 2 种模态的感知与交互能力（2026 年 12 月中期）。

**（2）测试依据**
课题任务书指标 1 中期要求；GB/T 25000.51 功能测试相关要求。

**（3）被测对象与前提**
- 已部署 UEnv Hub、Server、不少于 1 个 Worker。
- Hub 已注册文本类与结构化数据类环境包各 ≥1。
- 测试客户端可通过 Server Episode 接口提交任务并收取结果。

**（4）用例**

##### 用例 MM-01 文本模态输入解析与响应

| 项 | 内容 |
|---|---|
| 用例编号 | MM-01 |
| 检测目标 | 验证仿真环境能正确接收、解析文本观测/动作，并返回文本响应 |
| 前提条件 | 文本环境包已注册；Worker 心跳正常；准备纯文本样例 ≥10 条 |
| 操作步骤 | 1）通过 Hub 确认环境包版本与接口描述含 text observation/action；2）向 Server 提交 Episode，payload 仅含文本字段；3）Worker 执行 reset→step→close；4）导出轨迹，检查 observation/action/reward 字段 |
| 判定条件（通过） | ① ≥10/10 条 Episode 成功进入终态；② 轨迹中文本字段可解码且非空；③ 无协议错误、无 SYSTEM 失败；④ 任一失败可复现并记录为缺陷 |
| 判定条件（不通过） | 出现无法解析的文本输入，或无法产出文本响应，或 SYSTEM 失败率 >0（本用例样本量下） |

##### 用例 MM-02 结构化数据模态输入解析与响应

| 项 | 内容 |
|---|---|
| 用例编号 | MM-02 |
| 检测目标 | 验证表格/JSON 等结构化数据可被环境解析并参与交互 |
| 前提条件 | 结构化数据环境包已注册；准备 JSON 或表格样例 ≥10 条（字段含表头+单元格） |
| 操作步骤 | 1）提交仅含结构化数据字段的 Episode；2）执行完整生命周期；3）检查环境对结构化字段的解析日志与返回结构 |
| 判定条件（通过） | ① ≥10/10 成功终态；② 返回中含可解析的结构化对象（JSON Schema 校验通过或表格行列可还原）；③ 无因格式解析导致的 SYSTEM 失败 |
| 判定条件（不通过） | 结构化输入被当作纯文本丢弃字段，或无法生成结构化响应 |

##### 用例 MM-03 同框架双模态切换与对齐

| 项 | 内容 |
|---|---|
| 用例编号 | MM-03 |
| 检测目标 | 验证同一 UEnv 框架下可切换文本与结构化数据环境，观测空间语义对齐（字段映射一致、无串环境） |
| 前提条件 | MM-01、MM-02 所用环境包均可用；同一 Server 会话 |
| 操作步骤 | 1）连续提交文本 Episode 批次 A；2）不重启 Server，切换提交结构化 Episode 批次 B；3）再切回文本批次 C；4）比对 env_id、接口版本与轨迹模态标签 |
| 判定条件（通过） | ① A/B/C 三类批次均 100% 完成；② 轨迹中模态标签与请求环境一致，无串包；③ 切换过程无需改 Server 代码或更换集群，仅通过环境标识切换 |
| 判定条件（不通过） | 切换后出现环境串用、接口字段错位，或必须停服重建才能换模态 |

#### 4.2 测试项 2：智能体任务支持能力（中期）

**（1）指标内容**
具备单智能体任务执行能力；在文本阅读理解、表格理解、代码生成、测试生成、数学题求解 5 个基准任务上完成验证。

**（2）测试依据**
课题任务书指标 2 中期要求。

**（3）通用前提**
- 五个任务对应环境包均已在 Hub 注册。
- 每个任务准备 **评测子集 ≥50 条**（全量可更大，中期以可完成验证为准）。
- 单智能体：每个 Episode 由单一 Agent/策略接口驱动（不启用多智能体编排）。
- 记录项：准确率/通过率（不设中期硬阈值，除非主责单位书面要求）。

**（4）通用执行流程（五个用例共用，仅替换环境与数据）**

1. 在 Hub 核对环境包名、版本、依赖镜像。
2. Worker 拉取/就绪对应运行时（Process 或 Podman）。
3. 通过 Server 批量提交该任务评测子集。
4. 等待全部 Episode 终态；导出汇总：成功数、SYSTEM 失败数、BUSINESS 失败数、评测得分文件。
5. 抽检 ≥5 条轨迹，人工确认任务类型与输出格式符合该基准任务定义。

**（5）分用例判定**

| 用例 | 任务 | 数据集（建议） | 通过判定 |
|---|---|---|---|
| AG-01 | 文本阅读理解 | PubMedQA 子集 | ① 环境可执行；② 子集完成率 100%（允许 BUSINESS 失败，**SYSTEM 失败率 = 0**）；③ 产出标准评测结果文件 |
| AG-02 | 表格理解 | SciTab 子集 | 同 AG-01 |
| AG-03 | 代码生成 | DSCodeBench 子集 | 同 AG-01 |
| AG-04 | 测试生成 | 固化的测试生成环境包/子集 | 同 AG-01；另需证明输出为可识别的测试用例产物（文件或结构化字段） |
| AG-05 | 数学题求解 | OlymMATH 或 GSM8K 子集 | 同 AG-01 |

**指标 2 总判定**：AG-01～AG-05 **全部通过** 即中期指标 2 通过。

#### 4.3 测试项 3：运行稳定性（中期·百卡）

**（1）指标内容**
实现百卡规模下仿真环境服务的稳定运行（任务书：与主责单位协商确定具体量化指标）。

**（2）测试依据**
课题任务书指标 3 中期要求；稳定性量化口径采用本方案下列子集（建议会签主责单位后锁定）。

**（3）规模定义（建议写入正文并请主责单位确认）**

- **百卡口径**：参与本次稳定性测试的加速卡（GPU/NPU/DCU 等）合计 **≥100 张**；或主责单位书面确认的等效算力口径。
- **拓扑**：1×Server + ≥1×Hub + 多 Worker 节点；Episode 由 Server 统一调度。
- **中期负载量（可达成）**：在百卡就绪前提下，连续跑通 **≥100 万 Episode**（或连续运行 **≥24 小时** 且完成 Episode 数 ≥ 约定下限，二者与主责单位择一锁定）。
  - 说明：内部预研方案中的 1 亿 Episode / 5M 切片更适合终验或专项压测；中期采用缩规模，避免不可达。
- **已验证基线（报告中应引用）**：2 节点、最多 1024 Worker、43520 Episode、完成率 100%、Episode/RPC/协议错误为 0（季度材料）。中期测试是在该基线上的 **规模扩展验证**。

**（4）用例**

##### 用例 ST-01 百卡部署与服务可用性

| 项 | 内容 |
|---|---|
| 前提 | 百卡资源门禁通过；镜像与网络就绪 |
| 步骤 | 1）按拓扑部署；2）全部 Worker 注册成功；3）提交冒烟 Episode 每节点 ≥10；4）记录加速卡在线数 |
| 判定 | ① 在线加速卡数 ≥100（或确认口径）；② 冒烟完成率 100%；③ 控制面组件（Server/Hub）持续可用（测试窗口内非计划停服 = 0） |

##### 用例 ST-02 持续负载下系统失败率与完成率

| 项 | 内容 |
|---|---|
| 前提 | ST-01 通过；监控可采集 RSS/fd、Episode 终态原因 |
| 步骤 | 1）按约定总量或时长打入混合任务流（建议覆盖 ≥3 个已通过 AG 用例的环境类型）；2）标注 failure_reason=SYSTEM\|BUSINESS；3）统计完成率与 SYSTEM 失败率；4）可选：首/尾各 10% 窗口对比吞吐 |
| 判定（建议中期阈值，可达成） | ① Episode **完成率 ≥ 99.9%**；② **SYSTEM 失败率 ≤ 0.1%**（N\<1000 时 SYSTEM=0）；③ 无因资源耗尽导致的全集群不可用；④ 测试结束残留环境实例 = 0（`podman ps -a` / 进程 / 约定键空间扫描） |
| 记录项（不设硬阈值） | 吞吐保持率、RSS/fd 增长幅度（对照稳定性预研方案，供报告分析） |

##### 用例 ST-03 Server WAL 恢复零丢失

| 项 | 内容 |
|---|---|
| 前提 | Server 已开启 WAL；存在 in-flight Episode |
| 步骤 | 1）在负载中对 Server 执行 SIGKILL；2）按运维手册重启并重放 WAL；3）比对重启前后 Episode ID 与终态 |
| 判定 | ① 恢复后丢失 = 0、重复确认冲突 = 0；② P99 恢复时间 ≤ 约定值（建议 ≤ 300s，与预研 1s 量级区分：中期先保证正确性，时限可与主责单位确认）；③ 恢复后连续 ≥3 条真实 Episode 成功 |

##### 用例 ST-04 典型单点故障自动恢复

| 故障 | 注入方式 | 恢复时限（建议） | 判定 |
|---|---|---|---|
| Worker 进程退出 | SIGKILL | ≤ 120s | 自动恢复；连续 3 条 Episode 成功且结果一致 |
| 环境容器强杀 | podman kill | ≤ 120s | 同上 |
| 部分 Worker 网络阻断 | 防火墙阻断 60s | ≤ 120s | 同上 |
| 单节点隔离 | 安全组/VLAN 隔离 120s | ≤ 300s | 同上 |
| Server 退出 | SIGKILL（关联 ST-03） | ≤ 300s | 同上 |

每类故障注入 **≥3 次**（中期；预研方案 5 次可作终验加强）。任一次依赖人工登录节点执行重启命令才能恢复，则该次判失败。

**指标 3 总判定**：ST-01～ST-04 全部通过；量化阈值以本方案与主责单位会签版为准。

**降级说明（写进风险与进度，避免“测不了”）：**
若中期前百卡资源未到位，须在 T0 由项目层面确认：
- **A 方案（优选）**：延期正式 ST 至资源到位且仍赶得上 2026.12 报告节点；或
- **B 方案（需主责单位书面同意）**：以可达最大卡数完成 ST，报告中明确“未达百卡，不宣称中期指标 3 已满足”，并给出补测计划。
**不可**在未达百卡且无书面变更时，将小规模压测直接等同于中期指标 3 通过。
