## 1. 执行摘要

| 问题 | 结论 |

| Orchard Env 是否必须 K8s？ | **是，硬性依赖。** 官方仅提供 Kubernetes-native 部署路径，无 Docker 单机 / 裸进程替代方案。 |

## 2. Orchard Env 架构与 K8s 依赖依据

### 2.1 官方定位

Microsoft Orchard 将 **Orchard Env**（`orchard_env/`）定义为：

> A thin, **Kubernetes-native** environment service exposing generic primitives — sandbox lifecycle, command execution, file I/O, network policy, and a REST API.

来源：[microsoft/Orchard README](https://github.com/microsoft/Orchard)、[orchard_env/README.md](https://github.com/microsoft/Orchard/blob/main/orchard_env/README.md)

### 2.2 三层架构（均绕不开 K8s）

```
Client SDK (Python)
    │ REST
Orchestrator (FastAPI, 可多副本)
    │ K8s API — Pod 创建/删除/NetworkPolicy
    │ HTTP — 直连 Pod IP（exec/文件，绕过 API Server 热路径）
Sandbox Pod（用户镜像 + agent-injector initContainer + sandbox-tools）
```

关键设计（[architecture.md](https://github.com/microsoft/Orchard/blob/main/orchard_env/docs/architecture.md)）：

1. **Sandbox = Kubernetes Pod**，不是 Docker container 直连。
2. **NetworkPolicy（Calico）** 做默认 deny-egress 隔离；每个 sandbox 可选 per-pod allow-egress 策略。
3. **In-pod agent** 由 init container 注入，监听 `:9090`；orchestrator 通过 Pod IP 通信。
4. **多副本 orchestrator** 依赖 **Redis** 做分布式锁与状态共享（单副本可 `USE_REDIS=false`，但仍需 K8s 管 Pod）。

### 2.3 官方部署文档硬性前提

来源：[orchard_env/docs/deployment.md](https://github.com/microsoft/Orchard/blob/main/orchard_env/docs/deployment.md)

| 前提 | 说明 |
|---|---|
| **Kubernetes 集群** | ≥ 1.33 **推荐**（支持 `image` volume source 挂载 harness）；较老版本可退化为 `initcontainer` 模式 |
| **Calico NetworkPolicy** | 必须支持 NetworkPolicy；AKS 参考路径使用 Azure CNI + Calico |
| **节点标签** | sandbox Pod 需 `workload=sandbox` nodeSelector；参考部署还有 `NoSchedule` taint |
| **容器镜像仓库** | orchestrator、sandbox-agent-injector、sandbox-tools 等 4 个镜像需 push 到可达 registry |
| **Redis** | 默认 `USE_REDIS=true`；多副本 orchestrator 必需 |
| **工具链** | `kubectl`、`docker`（构建镜像）、Python 3.11+ |

> **Non-Azure clusters.** Only step 1 (provision) is Azure-specific. Any Kubernetes cluster with Calico NetworkPolicy, a `workload=sandbox` node label, and a reachable container registry works.

Azure AKS 仅是**参考自动化脚本**（`deploy_aks.sh` → `build_push.sh` → `deploy_k8s.sh`），**不是平台锁定**；但 **K8s 本身不可省略**。

### 2.4 是否存在“无 K8s”路径？

| 路径 | 是否可行 | 说明 |
|---|---|---|
| 官方 Docker Compose / systemd 单机版 | ❌ | 仓库无此产物 |
| 仅用 Docker API 替代 K8s | ❌ | orchestrator 源码基于 `kubernetes` client；sandbox 生命周期走 Pod CRUD |
| `IN_CLUSTER=false` 本地开发 | ⚠️ 仍需 K8s | 仅表示 orchestrator 用本机 kubeconfig 连集群，**不是**脱离 K8s |
| Modal / 其他云沙箱 | ❌ | 非 Orchard Env 官方支持范围 |

因此：**Orchard Env 环境侧 = 必须先有 K8s 集群。**

## 4. Orchard Env 部署组件清单

按官方 `deploy_k8s.sh` 顺序，完整栈包含：

| 组件 | 命名空间 | 资源需求（默认） |
|---|---|---|
| orchestrator Deployment | `orchestrator` | 控制面，可 HPA 多副本 |
| Redis | `orchestrator` | 状态/锁；可用集群内 Pod 或外部托管 |
| sandbox-orchestrator Service | `orchestrator` | ClusterIP + 可选 LoadBalancer |
| sandbox Pod（每个 sandbox） | `sandbox-pods` | **默认 4 CPU + 16 GiB**（request=limit） |
| RBAC / ServiceAccount | `orchestrator` | orchestrator 需 Pod CRUD、NetworkPolicy 权限 |
| NetworkPolicy | `sandbox-pods` | 命名空间级 deny-all-egress |
| 镜像（需构建 push） | — | `sandbox-orchestrator`、`sandbox-python`、`sandbox-agent-injector`、`sandbox-tools` |

### 4.1 参考 AKS 节点池（可缩放参考）

| 节点池 | 用途 | 参考规格 |
|---|---|---|
| `sys` | orchestrator + Redis + 系统组件 | `Standard_D8as_v5`（8 vCPU / 32 GiB），1–2 节点 |
| `sbx` | sandbox Pod | `Standard_D8as_v5`，autoscaler 1–50 节点，`workload=sandbox` + taint |

7143 若自建单节点 k3s，需在同一物理机上同时承担 sys + sbx 角色，并与现有 Docker 容器争用 CPU/内存/磁盘。

## 5. 7143 部署可行性评估

### 5.1 方案对比

| 方案 | K8s 需求 | 可行性 | 风险 | 建议 |
|---|---|---|---|---|
| **A. 7143 裸 Docker 直跑 Orchard** | 不需要 K8s | ❌ 不可行 | 架构不支持 | 放弃 |
| **B. 7143 上新建 k3s 单节点集群** | 本机新建 | ⚠️ 技术可行 | 与 uenv-worker/Docker 冲突；磁盘 92%；无 Calico 需额外安装 | 仅 PoC，不与生产 Worker 混部 |

### 5.2 方案 B（7143 自建 k3s）粗算资源

| 资源 | 估算占用 | 7143 余量 |
|---|---|---|
| k3s 控制面 + Calico | ~2–4 GiB RAM，2 CPU | 充足 |
| orchestrator + Redis | ~1–2 GiB | 充足 |

## 6. Orchard Env vs UEnv 7143 现有执行面

| 维度 | Orchard Env | UEnv Worker（7143 现状） |
|---|---|---|
| 编排底座 | **Kubernetes** | 裸机进程 + **Docker** |
| 沙箱单元 | K8s Pod + in-pod agent | Docker container / process plugin |
| 网络隔离 | Calico NetworkPolicy | Docker network / Gateway 层控制 |
| 状态/调度 | orchestrator + Redis | uenv-server DispatchEpisode + Worker Pool |
| 训练接入 | Python SDK → REST | gRPC Episode 协议 + Bridge/VeRL |
| SWE 场景 | Orchard-SWE recipe | OpenHands Gateway + SWE-smith 镜像 |
| 是否必须 K8s | **是** | **否**（当前生产路径不依赖 K8s） |

两者是**同层竞品**（见 `Docs/worker/260822/UEnv同类研究与竞品统计报告-20260822.md` §12.3），不是简单替换关系。若目标是在 7143 **叠加** Orchard 做对比评测，应走方案 E（远端 orchestrator）或方案 D（浦江 K8s），而非拆掉现有 Docker Worker。

## 7. 若要在 7143 相关环境落地 Orchard 的推荐步骤

### 7.1 推荐路径（浦江 K8s）

```text
1. 在浦江 K8s 确认 CNI 支持 NetworkPolicy（Calico 或兼容实现）
2. 申请/打标 sandbox 节点：workload=sandbox
3. 在 arm64 构建机 build_push Orchard 四镜像 → registry.h.pjlab.org.cn
4. 修改 k8s/configmap.yaml 中镜像引用与 DEFAULT_CPU/MEMORY（按节点规格下调）
5. 设置 SANDBOX_TOOLS_VOLUME_MODE=initcontainer（K8s 1.31）
6. deploy_k8s.sh 部署 orchestrator + Redis
7. smoke_test.sh 验证
8. 7143 或开发机 pip install orchard_env，SANDBOX_BASE_URL 指向 orchestrator LB
```

### 7.2 不推荐路径（7143 本机 k3s）的前置清理

若仍要做本机 PoC，至少需：

1. 清理磁盘至 <80%（删除无用 Docker 镜像/停止非必要容器）
2. 评估是否与 `uenv-worker` 争用端口（orchestrator 默认 8000）
3. 安装 k3s + Calico（或 k3s 自带 Flannel **不支持** NetworkPolicy 时需换 CNI）
4. 为节点打 `workload=sandbox` 标签
5. 单独规划 registry（7143 无 ACR，可用本地 registry 或 Harbor）

**与生产 UEnv Worker 同机混跑风险过高，建议用 7142 或阿里云扩展机做隔离 PoC。**

## 8. 风险与阻塞项

| 风险 | 级别 | 说明 |
|---|---|---|
| **K8s 硬依赖** | 阻塞 | 无 K8s 则无法部署；Docker alone 不够 |
| 7143 磁盘 92% | 高 | 镜像与 etcd/容器层叠加易打满 |
| 7143 无 K8s | 阻塞 | 需新建集群或换部署目标 |
| 浦江 arm64 vs Orchard amd64 镜像 | 中 | 必须 arm64 重构建 |
| K8s 1.31 < 1.33 | 低 | initcontainer 模式可绕过 image volume |
| Calico 依赖 | 中 | 非 Calico CNI 需验证 NetworkPolicy 行为 |
| 与 uenv-worker 资源冲突 | 高 | 同机混部影响现有 SWE 生产 |
| 默认 sandbox 16 GiB | 中 | 并发多时内存压力大；需调低 DEFAULT_MEMORY |
| 默认 deny-egress | 中 | SWE 任务需 `pip install`/模型 API 时要显式 `block_network=False` 或改 NetworkPolicy |

## 9. 结论与建议

### 9.1 直接回答

> **微软 Orchard Env 环境侧若要部署，是否必须 K8s？**
> **必须。** Orchard Env 从架构到官方部署文档均定位为 Kubernetes-native 服务；sandbox 即 Pod，隔离靠 NetworkPolicy，orchestrator 通过 K8s API 管理生命周期。不存在仅用 Docker 在 7143 裸机部署的官方支持路径。

> **7143 当前能否直接部署？**
> **不能。** 实机无 Kubernetes 集群。仅有 Docker/containerd 不足以运行 Orchard Env 控制面与 sandbox。

### 9.2 行动建议

| 优先级 | 行动 |
|---|---|
| P0 | 若要做 Orchard 评测：**部署目标选浦江 K8s**，而非 7143 本机 |
| P0 | 部署前确认浦江集群 CNI、NetworkPolicy、arm64 镜像构建链路 |
| P1 | 7143 可作为 **Orchard SDK 客户端** 连接远端 orchestrator，无需在本机起 K8s |
| P1 | 维持 7143 现有 **UEnv Docker Worker** 为生产主线，Orchard 作为竞品/PoC 平行环境 |
| P2 | 若必须本机 PoC：先解决磁盘、隔离 uenv-worker，再在独立机器（非 7143 生产）建 k3s |
| P2 | 对照 UEnv 规划中的 K8s-native Worker（`deploy/kubernetes/uenv-swe/`），评估是否复用同一集群节点池 |
