# UEnv 与原生 VeRL 调度算法对比实验方案

> 日期：2026-08-24  
> 范围：SWE-smith GRPO 训练链路下，UEnv+VeRL 与原生 VeRL（`native_swe_agent`）的**调度层**对比  
> 前置结果：[`uenv-bridge/docs/828季度会议准备/UEnv+VeRL与原生VeRL 20步对齐实验结果.md`](../../../uenv-bridge/docs/828季度会议准备/UEnv+VeRL与原生VeRL%2020步对齐实验结果.md)  
> 相关实现：[`Docs/adapter/20260823-原生VeRL-SWE-AgentLoop远端OpenHands执行说明.md`](../adapter/20260823-原生VeRL-SWE-AgentLoop远端OpenHands执行说明.md)

## 1. 文档目的

20 step 对齐实验表明：在**同资源、小批量、无故障**条件下，UEnv+VeRL 平均 step time 慢于原生 VeRL baseline，差距集中在 `rollout/gen`，训练更新侧基本持平。

本方案不从「单条 episode 最低延迟」争胜，而是从**调度算法与控制面能力**设计对比实验，使 UEnv 在合理工况下体现：

- 更高有效 episode 吞吐（`episodes/hour`）
- 更低排队等待与批屏障浪费
- 更强故障恢复与墙钟预算内的有效训练量

## 2. 对比定位（必读）

### 2.1 两条链路实际分工

| 层级 | 原生 VeRL（`native_swe_agent`） | UEnv+VeRL |
| --- | --- | --- |
| 训练算法 | VeRL GRPO | 同左 |
| AgentLoop | 训练进程内 `NativeSweAgentLoop` | 训练进程内 `UEnvAgentLoop` |
| 任务调度 | 本机轻量 `NativeAgentControlServer`（`:19051`） | `uenv-adapter-core` / Server（`:8088`） |
| Agent 执行 | 208.77 OpenHands poller | 208.77 OpenHands poller |
| SWE 沙箱 | **7143 Runtime Gateway**（共用） | **7143 Runtime Gateway**（共用） |
| 可观测 | 本地日志为主 | Obs run / episode / worker timeline |

**结论**：对比的是「是否经过 UEnv Adapter/Server 调度链路」，**不是**「完全不依赖 UEnv Worker 的环境实现」。两边 OpenHands + Gateway + harness 同源。

### 2.2 当前测试环境

| 项 | 值 |
| --- | --- |
| Benchmark | **SWE-smith**（`benchmark_variant=smith`） |
| 模型 | Qwen3.6-35B-A3B |
| 对齐规模 | 20 step；每 step 8 episode（`train_batch_size=2`, `rollout.n=4`） |
| Agent 并发 | 两侧约 4 slot（native：`poller.slot1..4`；UEnv：`openhands-uenv-align-qwen` 四 slot） |

### 2.3 20 step 结果对调度叙事的含义

| 观察 | 含义 |
| --- | --- |
| 平均 step 慢 ~17%，中位接近 | 不是「每步固定慢 17%」，而是**长尾 step 放大均值**（step 4/5 贡献约 59% 总差距） |
| `timing_s/gen` 为主因 | 差异在 rollout/环境交互调度，不在 actor/ref/update |
| 完成率均为 100% | 无故障工况下，UEnv 的 reclaim/容错优势**尚未被测到** |
| 同约 4 并发 | 小规模下 UEnv **多 Worker / 持续补槽** 能力未发挥 |

因此：**不宜**用 20 step 平均延迟证明 UEnv 全面更优；**应当**换工况与主指标。

## 3. 设计原则

### 3.1 允许的做法

- 将 native 固定为「训练进程内嵌的**朴素调度器**」语义（FIFO、批屏障、失败进队尾、单控制面）。
- 为 UEnv 启用完整控制面能力（容量感知、reclaim、多 Worker、持续补槽）。
- 通过**更大 batch、更高并发、故障注入、固定墙钟**放大调度差异。

### 3.2 禁止的做法

| 做法 | 原因 |
| --- | --- |
| native 内 `sleep` / 人为 RPC 重试 / 随机丢包 | 造假，日志不可辩护 |
| 故意减少 native slot（如 1）却给 UEnv 16 slot 且不披露 | 不公平对比 |
| 每 episode 新建 SSH（非正式 grpc 路径） | 差异来自传输栈，不是调度算法 |
| 未对齐样本顺序 / LLM config 却比 resolved | 混淆执行语义与调度 |

## 4. Native 侧：朴素调度语义（Baseline 定义）

正式对比路径：`NATIVE_SWE_EXECUTION_BACKEND=grpc` + 208.77 长驻 poller + 7143 Gateway。

### 4.1 四条固定规则

#### 规则 1：硬屏障批调度（Batch Barrier）

```text
每个 GRPO step：
  1) 一次性 enqueue 本 step 全部 N 条 episode
  2) 必须等 N 条全部 Complete
  3) 才进入 update_actor
  4) 禁止跨 step 预取下一批（无 pipeline / lookahead）
```

**预期开销**：任一长尾 episode 钉死整步；`barrier_waste = max(ep_i) - mean(ep_i)` 偏大。

#### 规则 2：无容量感知的 FIFO（Capacity-Blind FIFO）

| 行为 | Native | UEnv |
| --- | --- | --- |
| 派发 | 内存 deque 队头，谁 poll 给谁 | 看 pool load、Worker 容量、admission |
| 超订 | 允许队列深度 ≫ 总槽位 | 背压 / 准入 |
| 亲和性 | 无 gateway/worker 本地性 | 可按 Worker / pool 路由 |

实现参考：`uenv-bridge/src/uenv/bridge/native_agent_control_server.py` 中 `_queue: deque` + `PollAgentJob` 直接 `popleft`。

#### 规则 3：失败不 reclaim / 尾部重试（Fail-to-Tail）

```text
Agent 超时或 Complete 失败：
  - 不立即重派到队头（no reclaim-to-head）
  - 记 zero_reward 或整步失败；若重试则 append 到队尾
```

UEnv 对照：启用 Server 侧 `agent_job_reclaim_grace_secs` 等 stale 回收与优先重派。

#### 规则 4：单点控制面 + 单 Worker Gateway

- AgentControl **仅**在训练进程（7142）内。
- Gateway 固定单 Worker（7143），经反向 SSH 隧道供 208.77 访问。
- **不**给 native 接第二台 Worker 的智能路由（架构级约束，需在报告中写明）。

### 4.2 Native 最小代码约束（建议落地）

| 位置 | 约束 |
| --- | --- |
| `NativeSweAgentLoop.run_batch` | 禁止 step 间 enqueue；本 step 未齐不拉下一步 |
| `NativeAgentControlServicer.PollAgentJob` | 保持 FIFO；可选记录 `queue_depth` |
| `wait_result` 超时 | 不 `appendleft`；仅 fail 或 `append`（尾部） |
| 打点 | `enqueue_ts` / `dispatch_ts` / `complete_ts` 写入 metadata |

**不要**向 native 移植 UEnv 的 reclaim、multi-worker router、Obs 心跳（保持 baseline 朴素）。

## 5. UEnv 侧：应对照启用的调度能力

| 能力 | 说明 | 对比价值 |
| --- | --- | --- |
| Server 容量感知派发 | `/agents` 看 pool capacity / load | 降低空槽与排队 |
| 持续补槽 | agent 空闲即派下一条，pending 窗口可大于当前空闲槽 | 降低 batch barrier 浪费 |
| stale reclaim | agent 心跳丢失后 job 重派 | 故障工况有效吞吐 |
| 多 Worker | ≥2 台 Worker 注册，Server 按容量分发 | 扩展性拐点 |
| Obs 时间线 | run / episode / worker | 量化 queue_wait、slot 利用率 |

UEnv 配置参考：`UENV_AGENT_POOL_ID=openhands-uenv-align-qwen`；Server `8.130.75.157:8088`。

## 6. 三套对比实验（推荐执行顺序）

### 实验 S1：扩展性拐点（优先，2–3 天）

**问题**：随 Agent/Worker 槽位增加，谁的有效吞吐上升更快？

| 固定项 | 变化项 |
| --- | --- |
| 8 卡训练、SWE-smith 固定子集、同 harness | Agent slot：4 → 8 → 16（必要时加第二 Agent 机） |
| 每档跑满固定 episode 数（如 200）或固定 2h | UEnv 可选开第二 Worker |

**主指标**：

- `episodes/hour`
- 扩展效率：`throughput(N) / throughput(1) / N`（理想接近 1）
- `rollout_wait_ratio = rollout_time / step_time`

**决胜规则**：找最小 `N*` 使 `UEnv_eph(N*) > Native_eph(N*)`。小 N 允许 native 更快；大 N 预期 UEnv 追上并反超。

### 实验 S2：固定墙钟有效训练量（828 汇报主指标候选）

**问题**：相同墙钟 T（建议 6–12h）内，谁产出更多有效训练信号？

| 固定项 | 工况 |
| --- | --- |
| 同一 holdout 100 条（训练前/中/后 eval） | batch 提高至 16–32 episode/step |
| 两侧同模型、同 smith 子集 | 故障注入（见 S3）可选叠加 |

**主指标（按优先级）**：

1. holdout **resolve rate** 变化
2. **有效 episode 数** / **非零 reward episode 数**
3. 有效 GRPO step 数（失败重试后仍进入 update 的 step）
4. `episodes/hour`（辅）

**通过叙事**：holdout 持平或略优 + 有效 episode / 故障完成率显著更高 → UEnv 调度与控制面价值成立。

### 实验 S3：故障与恢复（调度优越性最硬）

| 注入 | 频率 | 主指标 |
| --- | --- | --- |
| kill 1 个 OpenHands poller | 每 30–60 min | episode 完成率、是否拖死整 step |
| Gateway 断 60–120s | ≥3 次 | MTTR、恢复后连续成功 episode |
| 训练 checkpoint resume | ≥2 次 | recover success、丢失 episode=0 |

**预期**：native 绑训练进程 + 隧道，故障面窄；UEnv Server 独立 + reclaim → **有效 episodes/hour** 与 **SYSTEM 失败率** 拉开差距。

## 7. 调度专用指标口径

### 7.1 必采（两侧统一打点）

| 指标 | 定义 | 采集 |
| --- | --- | --- |
| `queue_wait` | `poll_ts - enqueue_ts` | native metadata / UEnv Server 日志 |
| `slot_idle_ratio` | 有空闲 agent 槽但队列非空的时间占比 | poller + Server `/agents` |
| `barrier_waste` | `max(episode_latency) - mean(episode_latency)`  per step | VeRL step 日志 + episode 级耗时 |
| `rollout_wait_ratio` | `timing_s/gen / timing_s/step` | 训练日志 |
| `episodes/hour` | 完成 episode / 墙钟 | 汇总 |

### 7.2 辅采（训练侧已有）

| 指标 | 用途 |
| --- | --- |
| step time P50 / P95 | 长尾 vs 中位 |
| `timing_s/update_actor` 等 | 确认差异不在训练更新 |
| reward mean / 非零 reward 占比 | 短跑仅作信号，不作最终胜负 |

### 7.3 不作为「调度必胜」依据的指标

- 小规模、无故障下的平均 step time（native 短路径占优属结构结果）
- 同 harness 下的 holdout resolve **碾压**（执行语义对齐后无结构性保证）

## 9. 预期结论与汇报话术

### 9.1 分场景预期

| 场景 | Native | UEnv |
| --- | --- | --- |
| 小 batch、~4 并发、无故障 | 平均 step 可能更快 | 控制面固定开销可见 |
| 高并发、多 slot / 多 Worker | 吞吐平台期早到 | 扩展效率更高 |
| 故障注入 / 墙钟预算 | 有效 episode 损失大 | reclaim + 独立控制面更稳 |

### 9.2 推荐对外表述

> Native `native_swe_agent` 采用训练进程内嵌的 **FIFO + 批屏障** 调度；UEnv 采用独立控制面的 **容量感知派发、失败回收与多 Worker 扩展**。在小规模无故障对齐实验中 native 路径更短、平均 step 更快；在**高并发、故障注入与固定墙钟有效训练量**工况下，UEnv 预期在有效 episode 吞吐、排队等待与恢复能力上体现调度层优势。

**避免**：「UEnv 在所有 step 延迟上全面优于 native VeRL」。
